# Doctor Agent 快速开发准备与迭代计划

版本：`v0.1-draft`
目标：第一条产品功能开发线快速完成；另外两条线以 Mock 和稳定契约支持并行开发。

## 1. 开发原则

- 先做纵向可运行闭环，不先建庞大的平台。
- 产品功能是真实实现，Agent 能力是可替换 Mock。
- Mock 必须通过 API 和正式 Schema，不在 UI 内写死。
- 每两周至少完成一个医生可操作的纵向薄切。
- 安全、身份、权限和审计从第一天进入代码，不作为后补功能。
- 未确认内容使用 Feature Flag、Adapter 或配置隔离。

## 2. 技术栈（M0/M1 当前采用）

原 V4.3 HTML 的静态检查显示其使用 Vue 生态和 Element Plus 风格组件。为了最快复现既有 UI/UX，建议：

| 层 | 建议 | 理由 |
| --- | --- | --- |
| Web | Vue 3 + TypeScript + Vite + Element Plus | 与 Demo 体验最接近，减少页面重建成本 |
| 状态 | Pinia + TanStack Query 或等价方案 | 区分页面状态与服务端任务状态 |
| 产品 API | FastAPI 或现有医院标准后端 | AgentScope/Python 生态集成方便；最终待架构确认 |
| 契约 | OpenAPI + JSON Schema | 前后端、Mock、AgentScope Adapter 共用 |
| 实时状态 | SSE | 适合任务状态事件，复杂度低于 WebSocket |
| 数据库 | PostgreSQL | 任务、审计、版本和反馈结构化存储 |
| Mock | 版本化 JSON Fixture + Mock Runtime | 可重复、可回归、可故障注入 |
| 测试 | Vitest/Playwright + Pytest/契约测试 | 覆盖组件、端到端、API 和 Schema |

当前 M0/M1 已按下表建立可运行工程。如果医院后续指定技术栈，应保持产品交互和契约不变，仅替换实现技术。

## 4. 第一个纵向薄切：病情概况 + 风险管理

选择理由：

- 不依赖录音设备。
- 可先只读接入患者上下文。
- 能最早验证身份、数据时间、证据、卡片、风险和审计。
- 对三专科都适用。

### 4.1 产品线

- 登录与 Mock 环境标记；登录后直接进入医生智能体。
- 未选择患者状态、智能体内患者绑定，以及作为次级入口保留的候诊列表。
- 患者工作站骨架。
- 顶部患者安全条。
- 病情概况和风险两个功能入口。
- 成功、加载、澄清、失败、降级卡片。
- 查看依据、采纳、拒绝和反馈。

### 4.2 集成线 Mock

- 创建任务、任务事件、结果和动作 API。
- `condition_summary` 与 `risk_alert` Fixture。
- 超时、非法 Schema、身份错配和红色风险场景。
- Card View Model Mapper。

### 4.3 岗位与调优线 Mock

- 病情概况和风险岗位卡。
- 内分泌、骨科、妇科各 3–5 个 Mock 病例。
- 事实、证据、风险和冲突评分样例。
- 零容忍门禁测试样例。

## 5. 第二个纵向薄切：语音问诊 + 病历生成

### 产品线

- 录音控制、转写抽屉和纠错。
- 结构化问诊结果。
- 病历编辑器、逐段生成、采纳和差异。
- 暂存、模拟提交和审计。

### 两条 Mock 线

- 固定音频/转写 Fixture。
- 低置信、说话人错误和关键澄清场景。
- 病历分段结果、来源映射和事实冲突。
- 不可覆盖医生文本和未经确认写回的安全测试。

## 6. 第三个纵向薄切：鉴别诊断 + 诊断管理

### 产品线

- 候选诊断卡。
- 支持/反对证据和下一步。
- 主诊断、次诊断、待排诊断管理。
- ICD 候选、排序、合并、删除和变更原因。

### 两条 Mock 线

- 同一诊断 Agent 的两类任务结果。
- 高危必须排除项。
- 待排与确诊错误场景。
- 诊断与病历/检验冲突场景。

## 7. 第四个纵向薄切：共病管理与完整闭环

- 三专科共病问题清单。
- 管理目标、行动、随访和转诊建议。
- 与本次主诉相关性和优先级。
- 七功能统一任务中心。
- 模拟写回、审计、反馈和评测样本候选池。

## 8. 建议迭代节奏

| 阶段 | 产品功能开发条线 | Agent 集成 Mock | 岗位与调优 Mock | 验收物 |
| --- | --- | --- | --- | --- |
| M0 基础 | 工作站壳、路由、设计系统 | Schema v1、Mock Gateway | 岗位卡模板、Fixture 规范 | 能创建任务并显示完整状态 |
| M1 概况+风险 | 智能体直达、患者绑定、两类结果 | 概况/风险结果与故障注入 | 两岗位卡、三专科样本 | 只读纵向薄切 |
| M2 问诊+病历 | 转写、编辑、逐段采纳 | 语音/病历任务与来源映射 | 两岗位卡、事实门禁 | 从采集到文书 |
| M3 诊断 | 鉴别和诊断管理 | 双任务路由、诊断 View Model | 诊断岗位与高危回归 | 诊断闭环 |
| M4 共病+收口 | 共病、任务中心、写回队列 | 共病、审计、Mock 写回 | 共病岗位、完整评测流 | 七功能可演示产品 |

具体日历和人员排期待确认；阶段顺序可并行，但每个阶段必须形成可运行版本。

## 9. 首批开发任务

### 9.1 产品功能开发条线

1. 建立 Web 工程、路由和原 HTML 基础布局，不重做 UI/UX。（M0 已完成）
2. 实现登录后直达医生智能体、未选择患者状态和患者绑定；候诊列表作为次级入口保留。（M1 已完成）
3. 实现患者安全信息、患者切换隔离和上下文清空。（M1 已完成）
4. 复用原 HTML 功能导航并接入统一任务状态机。（M0/M1 已完成基础版）
5. 实现通用结果卡、证据、澄清和失败组件。
6. 实现病历编辑器与段落级 AI 草稿层。
7. 实现诊断候选和诊断列表组件。
8. 实现风险条和共病问题清单。
9. 实现医生动作、模拟写回和任务详情。
10. 完成 E2E 与桌面端 UI 验收。

### 9.2 Agent 集成条线

1. 冻结五个核心 Schema v1。（已生成 OpenAPI/JSON Schema）
2. 建立 Mock Agent Gateway。（已完成基础版）
3. 实现任务状态事件和 SSE。（API 已完成；前端当前使用安全轮询，SSE 接入待下一轮）
4. 实现语义结果到卡片的 Mapper。（已完成七类组件映射基础版）
5. 建立 Adapter 接口和 Mock Runtime。
6. 建立 Skills/MCP/数据注册表空壳。
7. 实现身份、权限、Schema 和安全校验。
8. 实现审计和 Trace。
9. 实现故障注入和降级。
10. 为 AgentScope 接入准备联调清单。

### 9.3 Agent 岗位定义和调优条线

1. 完成六张岗位卡 v0.1。
2. 完成 Context Bundle v1。
3. 定义三专科 Mock 患者与场景矩阵。
4. 编写各 Agent 成功/缺失/冲突/风险/失败 Fixture。
5. 建立评测样本 Schema。
6. 建立通用与岗位指标。
7. 建立六项零容忍门禁。
8. 建立错误分类与回归报告模板。
9. 建立医生反馈到样本候选池的流程。
10. 形成 Worker、Skill、Sub-agent 讨论稿，明确标注“待讨论”。

## 10. 测试策略

### 10.1 产品测试

- 组件状态快照。
- 七功能用户流程。
- 患者切换和任务隔离。
- 权限和未授权。
- 编辑、部分采纳、拒绝和恢复。
- 原 HTML 已有桌面布局及其既有分辨率适配行为，不新增布局方案。

### 10.2 契约测试

- 请求、事件、语义结果、卡片和审计 Schema。
- 向后兼容。
- Mock Adapter 与 AgentScope Adapter 的共享测试套件。
- 非法字段、缺字段和未知枚举。

### 10.3 安全测试

- 身份错配。
- 越权患者。
- 未确认写回。
- 红色风险漏报。
- 旧任务结果串入新患者。
- 失败结果或非法 Schema 进入页面。

## 11. 环境建议

| 环境 | 数据 | Runtime | 用途 |
| --- | --- | --- | --- |
| Local | 固定 Mock | Mock | 开发与组件测试 |
| Dev | 版本化 Mock | Mock/AgentScope 开发环境 | 联调 |
| UAT | 去标识化病例 | Mock + 受控 AgentScope | 医生验收 |
| Shadow | 真实只读数据 | AgentScope | 影子评估，不写回 |
| Production | 正式授权数据 | AgentScope | 通过门禁后逐步开放 |

## 12. 版本与 Feature Flag

建议至少提供：

- `runtime.mock.enabled`
- `runtime.agentscope.enabled`
- `feature.voice_interview.enabled`
- `feature.condition_summary.enabled`
- `feature.record_generation.enabled`
- `feature.differential_diagnosis.enabled`
- `feature.diagnosis_management.enabled`
- `feature.risk_management.enabled`
- `feature.comorbidity_management.enabled`
- `write_back.mode=mock|disabled|real`
- `specialty_package.endocrinology|orthopedics|gynecology`

临床安全开关只能从安全方向降级：例如真实写回可关闭，不能绕过医生确认。

## 13. 开发过程中待确认

- 医院是否要求替换当前前后端技术栈。
- 是否能够取得 V4.3 Demo 的未压缩源工程；当前已按确认的 HTML 外观和交互重建可维护组件。
- 本地、Dev 和 UAT 的运行环境。
- 产品登录方式与医生/科室数据来源。
- 首批 Mock 患者是否沿用 Demo 内分泌患者。
- 三条线的负责人和日常决策机制。

上述事项不阻塞 M0 文档、契约、Mock Fixture 和 UI 组件准备，但会影响正式工程初始化。

## 14. 整体 Definition of Done

- 七个功能均可在完整门诊工作站中操作。
- 页面不依赖真实 Agent 即可通过全流程 UAT。
- Mock 与未来 AgentScope 使用同一请求、事件和结果契约。
- 所有结果可查看依据、编辑、采纳、拒绝和反馈。
- 所有关键动作可审计。
- 六个 Agent 岗位和评测框架已版本化。
- 六项零容忍门禁可自动验证。
- 未确认写回、身份错配和跨患者结果串用均为 0。

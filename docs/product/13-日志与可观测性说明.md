# 日志与可观测性说明

面向后续的测试、排障与调优。回答一个问题：**出问题时，去哪儿看、看什么。**

---

## 0. 现在有四层，各管一段

| 层 | 存在哪 | 保留多久 | 回答什么问题 |
| --- | --- | --- | --- |
| **审计日志** `audit_logs` | SQLite | 永久 | 谁在什么时候做了什么（合规追溯） |
| **运行日志** `agent_runs` | SQLite | 永久 | 某次岗位调用的输入摘要、输出、耗时、token |
| **结构化事件** stdout | 容器日志 | 随容器 | 按时间顺序发生了什么、为什么降级、哪条被拦 |
| **前端日志** 内存环形缓冲 | 浏览器 | 当前页面 | 用户这一路点了什么、哪一步慢 |

**为什么四层不是冗余**：审计要长期可查且不可篡改，运行日志要能翻出当时的输出，
结构化事件要能 `grep` 出全局规律，前端日志要能看清「用户视角发生了什么」。
把它们合成一层，必然在某个场景下不够用。

## 1. 后端结构化事件

代码在 `apps/api/app/obs.py`。单行 JSON 打到 stdout，容器日志直接 `jq`。

### 埋了哪些点

| 事件 | 位置 | 关键字段 | 为什么埋这里 |
| --- | --- | --- | --- |
| `llm_call` | `llm.py` | `agent / model / attempt / request_bytes / status / ms` | 通道层事实。`attempt` 能看出重试了几次 |
| `agent_run` | `agents/base.py` | `agent / patient / tier / model / ms / tokens / version / source` | 岗位跑成功的基线。**带上 version 与 source** —— 排查「今天怎么变慢了」时，第一个要排除的就是「是不是换了配置」 |
| `agent_degraded` | `agents/base.py` | `agent / patient / reason / detail / tier` | **最需要事后追查的一类**。界面只显示「已降级」，为什么降的只有日志知道。`reason` 记异常类型不记消息 —— 类型能聚合计数，消息各不相同 |
| `redline_blocked` | `routers/emr.py` | `patient / action / open_count / open_ids` | 零容忍门禁真正生效的证据 |
| `redline_passed` | `routers/emr.py` | `patient / action / handled` | 放行也要记：只记拦截的话，「那次到底走没走这条路」查不出来 |
| `eval_run` | `routers/admin.py` | `agent / total / passed / failed / datasets / failed_cases` | **通过率必须连着分母与失败清单**，否则日后分不清是「改好了」还是「关掉了半个数据集」 |
| `eval_dataset_toggle` | `routers/admin.py` | `dataset / enabled` | 同上，「那次为什么没跑到」要能查 |

### 字段命名必须跨事件一致

耗时一律叫 `ms`，不叫 `elapsedMs`。`llm_call` 原本自己拼 JSON 用的是驼峰，
结果 `jq 'select(.ms>15000)'` 会**静默漏掉整整一类** —— 偏偏它正是排查
「哪一步慢」时最该看的一类。已统一走 `obs.event`，有测试守着
（`test_all_events_share_one_field_vocabulary`）。

输出用**紧凑分隔符**（`{"event":"agent_run",...}`）。`json.dumps` 默认会输出
`"event": "agent_run"`，让 `grep '"event":"agent_run"'` 匹配不上 ——
而 grep 是排障时最顺手的第一道筛子。同样有测试守着。

### 硬约束：正文绝不进日志

`obs.py` 里有一张 `_REDACTED` 表，`prompt / role_prompt / safety_layer / content /
fields / output / reply / api_key` 等键**一律换成长度**：

```json
{"event":"agent_run","agent":"record","patient":"P001","prompt_len":1842,"ms":8900}
```

一期是虚构数据，但**日志会被复制进工单、粘进聊天**，这个习惯必须现在就立住。
要看内容去 `agent_runs` 表，那里有权限边界。

有测试守着这条：`test_event_never_logs_content`。

### 怎么查

```bash
# 全部降级事件
ssh ubuntu@81.71.155.220 'sudo docker logs doctor-agent-mvp 2>&1' \
  | grep '"event":"agent_degraded"' | jq .

# 某个病例的完整链路
... | jq 'select(.patient=="P001")'

# 超过 15 秒的岗位调用
... | jq 'select(.ms>15000)'

# 今天各类降级原因的计数
... | jq -r 'select(.event=="agent_degraded") | .reason' | sort | uniq -c
```

## 2. 前端结构化日志

代码在 `apps/web/src/logging.ts`。挂在 `window.__da`。

### 默认关闭，但一直在记

**关闭的只是控制台输出，缓冲始终在记。** 理由：出问题往往是事后才想起要看日志，
那时再打开开关重现一遍，现场早没了。缓冲是环形的，上限 500 条。

三种打开方式：

```
https://da.aaronhealth.cn/outpatient/list?debug=1   # 写进 localStorage，后续会话有效
__da.on()                                            # 控制台
localStorage.setItem('da_debug', '1')
```

### 排障命令

| 命令 | 作用 |
| --- | --- |
| `__da.dump()` | 打成表格看（时间 / 模块 / 事件 / 耗时 / 详情） |
| `__da.json()` | 导出成 JSON，直接贴进工单 |
| `__da.slow(1000)` | 只看耗时超过 1 秒的。**阈值默认 1 秒** —— 首屏聚合本来就十几秒，再低全是噪音 |
| `__da.clear()` | 清空 |
| `__da.off()` | 关闭输出（缓冲继续记） |

### 埋了哪些点

控制台（`useAdminConsole.ts`）：`select_agent / save_draft / publish / rollback /
compare / run_eval / eval_result / toggle_dataset`。
移动端控制台另有 `switch_pane`。

`time()` 包裹的调用**成功与失败都落一条，且失败也带耗时** ——
「失败得多快」本身是线索：3ms 失败多半是本地校验，20s 失败多半是网关超时。

---

## 3. 加新埋点时的三条规矩

1. **事件名用下划线小写，且是名词性的事实**（`agent_degraded`），
   不是动作描述（`degrading agent now`）。前者能聚合计数，后者不能。
2. **失败路径必须也记耗时。** 只记成功的话，最需要日志的那一刻反而什么都没有。
3. **只记标识与度量，不记正文。** 新字段若可能含正文，加进 `obs.py` 的 `_REDACTED`。

---

## 4. 还没有的（有意为之）

- **没有接 APM / Langfuse**：一期单容器，容器日志 + SQLite 够用。
  接第三方意味着病历相关的调用链要出网，那是需要单独评估的事。
- **前端日志不上报服务端**：上报就等于把用户操作轨迹送出浏览器，
  在医疗场景要先过合规。现在是「出问题时手动导出」。
- **没有采样**：量还很小，全量记更有用。

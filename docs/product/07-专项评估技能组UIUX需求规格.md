# Doctor Agent 专项评估技能组 UI/UX 需求规格

版本：`v0.2-draft`  
日期：`2026-08-29`  
状态：产品信息架构与 Mock 交互可实施；Worker/Sub-Agent 拆分、正式上线范围待专题讨论

## 1. 文档目的

本文件定义原 AI-HIS 页面右下角“专项评估小助手”的产品定位、五类助手、33 项专项能力、交互状态、Agent 集成边界和测试要求。界面沿用最早 HTML 的折叠列表、淡色分组和内嵌说明，不另建新的门户或工作台。

> **命名与默认态（2026-09-02）**：标题由“专项评估”改为“专项评估小助手”；
> 五个分类**默认全部折叠**。一期只做目录展示、33 项都还没 Agent 化，
> 铺开会占掉大半屏、把下面真正在用的内容挤没 —— 折叠起来当索引用。
> 展开态本身仍与 V4.3 原件一致。

“专项评估”不是一期第八个核心产品功能，也不等于 33 个已经确定的独立智能体。它是医生个人助手方向的能力目录和场景入口：能力可以由规则、Skills、MCP、现有六个 Agent 或未来专项 Worker 承载。具体 Worker/Sub-Agent 岗位拆分统一标记为**待讨论**。

## 2. 决策依据

1. 最早 HTML 原件及用户提供的专项评估截图。
2. 2026-08-12 阶段性汇报会会议纪要：医生个人助手围绕临床、科研、教学、运营、患者服务五个“秘书”方向细化并形成分级方案。
3. 同一会议明确：可独立对外输出的能力可考虑作为 Sub-Agent，否则优先定义为 Skills；颗粒度仍需边做边讨论。
4. 一期七功能、六 Agent 的既定边界不变。

## 3. 产品定位与五个秘书映射

| 页面分组 | 秘书方向 | 产品职责 | 一期技术定位 |
| --- | --- | --- | --- |
| 诊疗质控助手 | 临床秘书 | 诊疗质量、专病风险、院感、不良事件、报告和危急值闭环 | 复用 F02/F04/F06、规则和专项 Skills |
| 患者服务助手 | 患者服务秘书 | 筛查、转诊、慢病管理、检查引导、教育和康复服务 | Mock 技能目录；后续对接患者智能体/服务平台 |
| 运营管理助手 | 运营秘书 | 权限、预约、医保、费用、资源和绩效 | Mock 技能目录；后续对接运营规则与数据服务 |

## 5. UI/UX 规格

### 5.1 区域与层级

- `UI-SA-001` “专项评估”位于原 HTML 中间 AI 助手区域右下方、智能笔记之后，保留原三栏布局。
- `UI-SA-002` 首层为五个助手分组，显示分组名称、项目数量和展开/收起符号。
- `UI-SA-003` 第二层为专项能力行，整行可点击；右侧使用箭头表示可展开，不使用新的大卡片覆盖页面。
- `UI-SA-004` 展开能力后在原行下方显示一段简要用途说明；说明以医生任务为中心，不呈现模型思维链。
- `UI-SA-005` 五类分组使用原截图的淡色区分：诊疗质控淡红、患者服务淡绿、运营管理淡黄、科研淡蓝、教学淡绿；颜色只用于分组，不代表临床风险等级。
- `UI-SA-006` 红黄风险只在“风险提示/风险预警”区域表达，专项评估的淡红/淡黄背景不得被解释为患者风险。
- `UI-SA-007` 页面首次进入、刷新和切换患者后五个助手分组默认全部折叠；医生可独立展开任一分组，收起时同步收起该组已打开的能力说明，并保留页面滚动位置。
- `UI-SA-008` 专项能力运行后，在该行内显示 `准备中/运行中/需补充/已完成/失败/降级`，不得弹出另一套聊天工作台。
- `UI-SA-009` 结果优先使用结构化卡片、清单、表格或草稿；长依据进入原有详情组件。
- `UI-SA-010` 面向医生的界面不显示“Mock 效果”按钮；Mock 身份进入结果详情和审计元数据。
- `UI-SA-011` 鉴别诊断中的 `must_not_miss` 候选或带 `risk_links` 的候选，在卡片左下方显示“风险预警”入口、关联风险数量和“查看详细”；普通候选不显示该入口。
- `UI-SA-012` 点击“风险预警”只负责定位 F06 权威风险页，不在鉴别诊断内复制处置状态。
- `UI-SA-013` 顶部功能页签统一使用“风险预警”，不再混用“预警评估”“风险管理”等医生入口名称；接口任务名仍为 `risk_management`。
- `UI-SA-014` 风险详情至少显示等级、标题、影响与门禁、关键证据、来源与数据时间、阈值/判定、反证与不确定性、关联专项评估、关联 Skills、处置时限和状态。
- `UI-SA-015` 风险列表默认折叠详情；医生点击“查看详细”展开单项，再次点击收起。允许查看多项，但一期默认一次只展开一项，切换患者或任务版本后全部收起。

### 5.2 点击后的交互状态

| 状态 | 页面行为 | 允许动作 |
| --- | --- | --- |
| `idle` | 仅显示能力名称和用途 | 启动评估 |
| `unavailable` | 显示缺患者、权限或数据条件 | 查看缺失条件 |
| `preparing` | 显示准备的数据域 | 取消 |
| `running` | 行内进度，不展示未校验结果 | 取消、继续其他工作 |
| `needs_clarification` | 展示待补字段和原因 | 补充、放弃 |
| `ready` | 显示结构化结果和证据摘要 | 查看详情、采纳草稿、拒绝 |
| `failed/degraded` | 说明失败域和降级能力 | 重试、人工处理 |

## 6. 调用与集成边界

### 6.1 调用阶段

每次调用必须绑定 `patient_id`、`encounter_id`、`doctor_id`、`organization_id`、`assessment_id` 和用户触发动作。没有患者上下文的运营/教学类能力，如确需独立运行，应进入未来独立入口，不能借用当前患者上下文。

### 6.2 执行阶段

建议产品调用格式：

```json
{
  "assessment_id": "clinical_quality.disease_risk",
  "patient_id": "P001",
  "encounter_id": "E001",
  "requested_by": "doctor",
  "context_refs": ["diagnoses", "vitals", "labs", "medications"],
  "mode": "mock"
}
```

执行编排可调用现有 Agent、Skills、MCP 或规则服务。产品层只依赖统一任务协议，不直接依赖某个 Worker 名称。

### 6.3 返回阶段

返回至少包含：

- `assessment_id`、名称和所属助手；
- 状态、摘要和结构化结果；
- `evidence_refs`、数据截止时间和缺失数据域；
- 风险或质控事项及其等级；
- 推荐动作草稿、是否需要医生确认；
- Runtime、Skill/MCP、规则和数据版本；
- 患者/就诊一致性、权限和审计信息。

专项评估发现临床风险时，不在自身结果中维护第二份闭环状态；应向 F06 上报统一风险项并保存 `risk_id` 引用。

## 7. 数据、Skills 与 MCP 候选

| 助手 | 主要数据 | Skills 候选 | MCP/服务候选 |
| --- | --- | --- | --- |
| 诊疗质控 | 病历、诊断、检查检验、生命体征、用药、操作、危急值 | 质控规则编排、风险分层、证据归并 | EMR、LIS、RIS/PACS、危急值、院感/不良事件系统 |
| 患者服务 | 患者档案、随访、预约、服务包、宣教、设备数据 | 服务匹配、转诊草稿、宣教生成 | 预约、患者智能体、短信/企微、设备平台 |
| 运营管理 | 权限、排班、医保、费用、资源和绩效口径 | 合规校验、资源分析、指标解释 | 权限、医保规则、收费、排班、BI/绩效服务 |
| 临床科研 | 研究方案、入排标准、授权后的去标识化数据 | 方案解析、候选匹配、证据核验 | CTMS/EDC、伦理、科研数据平台 |
| 临床教学 | 脱敏病例、教学目标、点评规则、题库和教学记录 | 病例脱敏、要点提取、点评/题目草拟 | 教学平台、题库、教学档案服务 |

所有数据访问遵循最小权限；科研和教学不得默认使用可识别患者信息。

## 8. 业务与安全规则

- `BR-SA-001` 专项能力目录、启用范围、输入数据和输出模板均版本化，可按医院、科室和角色配置。
- `BR-SA-002` 同一能力的运行结果绑定当次患者/就诊和上下文哈希；关键数据变化后旧结果标记过期。
- `BR-SA-003` 能力不可用时不得用静态文案冒充真实结果；Mock 数据通过相同 Schema 和患者隔离校验。
- `BR-SA-004` 专项能力只生成建议、草稿或待办，不自动完成报告、转诊、入组、医保审核、绩效核算或教学评价。
- `BR-SA-005` F06 风险和危急值等医院权威闭环状态不能由专项评估自行关闭。
- `SAFE-SA-001` 跨患者、跨就诊、越权、科研未授权、教学未脱敏均为零容忍问题。
- `SAFE-SA-002` 医保、绩效、科研和教学输出必须显示适用口径、版本和人工复核责任。
- `SAFE-SA-003` 任何能力都不得展示内部推理链或把模型建议伪装成医院正式规则。

## 9. Mock 与测试数据要求

1. 五类助手各至少一项可操作 Mock；诊疗质控至少覆盖红色风险、黄色风险和无风险三种结果。
2. Mock 仍使用真实任务状态和 Schema，不提供独立“生成 Mock 效果”按钮。
3. 内科、骨科、妇科分别准备一个专病风险评估示例。
4. 运营、科研、教学使用去标识化或虚构数据，禁止读取真实绩效和真实研究候选人。

## 10. 验收标准

- `AC-SA-001` 五类助手及 33 项名称、数量与已确认截图一致。
- `AC-SA-002` 分组和能力均可展开收起，说明文字不遮挡智能笔记和主病历。
- `AC-SA-003` 分组淡色与红黄临床风险在文字、图标和语义上明确分离。
- `AC-SA-004` 点击能力后完整经历任务状态，不展示虚假成功结果。
- `AC-SA-005` 产生的患者风险统一引用 F06 `risk_id`，不会产生两份相互冲突的闭环状态。
- `AC-SA-006` 每次调用可追溯患者、就诊、操作者、数据、Skill/MCP、规则和版本。
- `AC-SA-007` 患者切换、权限变化和迟到响应均不会导致结果串用。
- `AC-SA-008` 五个助手首次加载全部折叠；仅展开医生点击的分组，收起分组后不残留能力说明。
- `AC-SA-009` 带风险关联的不能漏诊候选显示“风险预警”入口，并可直达当前患者、当前就诊的 F06 页面。
- `AC-SA-010` 风险详情信息完整且缺失字段有安全降级文案；不得以空白、`undefined` 或模型推测补齐。

## 11. 待讨论

- 每一项能力是 Skill、Worker/Sub-Agent 还是规则服务，以及是否具备独立对外输出资格。
- 五个秘书是否作为主 Agent、导航分组或医生智能体内的岗位视图。
- 一期仅演示哪些专项能力，二期/后续正式建设哪些能力。
- 运营、科研、教学的产品负责人、数据负责人、审批人和 UAT 口径。
- 专项评估与患者智能体、科研平台、教学平台、运营系统的正式接口边界。

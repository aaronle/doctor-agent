## 4. 功能规格

每个功能按「触发 → 输入 → 处理 → 输出 → 医生动作 → 约束 → 验收」描述。所有 Agent 输出一律**先落草稿区，经医生确认才进入病历/医嘱**。

### F01 语音问诊

对齐 V4.3 的交互模型：**点一下自动播放本次就诊的对话脚本**，播放过程中浮出「AI 追问提示」与「补充观察」。

- **触发**：医生智能体面板 `● 语音问诊`。
- **状态机**：`idle` → `playing` → `awaiting` ⇄（继续问诊）→ `ended` →（继续问诊）→ `awaiting`
  - **「内容播完」不等于「问诊结束」**。播完只进 `awaiting`，医生仍可继续录入；结束由医生点。两个理由：
    1. 正式环境是连续音频流，根本没有「播完」这个事件。靠静音判断会把医生查体、思考、敲字的停顿误判成结束，把问诊拦腰切断。
    2. 结束会触发病历与全部分析的重新生成，属于有后果的动作，必须医生确认。
  - 这样 MVP 的状态机与正式环境一致：接 ASR 时只是把「脚本推进」换成「音频流推进」，结束仍然是医生点的。
  - `awaiting` 期间问诊仍算进行中，两个浮层继续留着。
- **界面只有两个按钮**，构成一个可重复的循环，医生不需要判断该点哪个：

  | 按钮 | 做什么 |
  | --- | --- |
  | `▶ 继续问诊` | 继续启动语音录入 —— 跟患者对话，或医生自己补充内容。脚本没播完就接着播；已播完则切回可录入状态，不假装还有可播的。问诊进行中时显示为 `● 问诊进行中` 并禁用。 |
  | `■ 结束问诊` | 落库问诊记录 → 重算病情概况/鉴别诊断/风险/共病 → 重新起草病历。一次做完全部下游生成。 |

  结束后仍可点「继续问诊」接着录，再点「结束问诊」按最新内容重新生成。
- **为什么结束必须触发下游生成**：病情概况、鉴别诊断、风险、共病都是**打开工作站时**算好的，也就是在问诊之前。不在结束时回灌一次，医生问出来的新信息就进不了那些面板，这一场问诊等于白做。病历同理。执行顺序里落库必须在最前 —— 下游上下文（`latest_dialog`）读的是持久化后的记录。
- **界面元素**：
  - `msg-bubble.doctor|patient` 医患对话气泡，**逐条上屏**（间隔 1400ms），不是一次性刷出
  - `pending-float` 「AI 追问提示」浮层：当前该问的一条带编号高亮，已问到的落入 `pq-done-list` 打勾划掉
  - `obs-float` 「补充观察」浮层：**待观察清单**，问诊开始即自动浮出（不藏在按钮后面），可勾选，勾中的并入问诊小结
  - `mode-badge.voice` 患者标签上的「语」徽标
  - `action-bar`：`● 语音问诊`（未开始）/ `▶ 继续问诊` + `■ 结束问诊`（问诊中）
  - `chat-toolbar`：`＋`（上传/提示词）+ `接诊下一位` / `报告解读` / `鉴别诊断`
- **追问清单的覆盖判定（语义，非顺序）**：`pending-float` 里划掉哪几条，由 `POST /api/emr/voice/coverage` 判定。
  - **为什么必须用模型**：覆盖是**蕴含关系**不是相似关系。「哪一侧肢体无力？」被「右手拿筷子拿不稳，右腿走路也有点拖」完整回答，两句几乎零字面重叠 —— 关键词匹配与向量相似度都会在这里大面积漏判。
  - **清单必须是原子问项**：实测同一段对话，清单为原子问项时 15 条判定全对、三次运行完全一致；换成复合问句（「在做什么，有没有诱因？」）则稳定判错。难点不在模型能力，在清单本身，因此 `VoicePlanAgent` 强制「一条只问一件事」。
  - **判错方向必须安全**：漏标已问 = 医生多扫一眼；错标已问 = 该问的问题再也不提醒。因此规则是「必须引用到患者原话，拿不准一律判未覆盖」，且**降级时不做任何标记**，不退回关键词或按轮次猜。
  - **单调 + 增量**：已标记不回退，每次只发还开着的问题与对话增量。
  - **异步非阻塞**：判定在后台跑，界面任何时候不等它。
  - **医生可手动勾销**：点击清单条目即可标记/撤销，模型判错时一键纠正。
- **待观察的动态过滤**：`obs-float` 里列的是**还没问到的**条目。判定沿用 V4.3 —— 去掉「有无/是否」等问法前缀后取前三个字，在已播出的对话全文里做包含匹配，命中即从清单移出。静态清单看着一样，但医生分不清哪些已经问过。
- 相应地，上下文装配（`latest_dialog`）**优先取医生实际做过的那场问诊**，没有才退回演示脚本。
- **正式环境与 MVP 的差别只在「声音怎么进来」**：正式环境由 ASR 实时转写医患对话；MVP 播放种子里的 `dialog_script`。上屏节奏、追问清单、待观察、问诊小结在两种环境下完全一致，接入 ASR 时前端与 Agent 都不需要改。
- **分工**：对话脚本是**演示数据**（种子 `dialog_script`）；追问清单与补充观察是**真实模型输出**。
- **约束**：模型只产出**给医生的追问清单与观察项**，不得代替医生向患者提问，不得据此下诊断；勾选的观察项需医生确认才进入病历。
- **验收**：
  - 对话逐条上屏，不是一次性刷出
  - 追问清单随对话推进逐条划掉
  - 待观察清单里已被对话覆盖的条目自动移出
  - 暂停 / 继续 / 重新问诊三态可切
  - **内容播完只进 `awaiting`，只有医生点「结束问诊」才转 `ended`**
  - `awaiting` 期间浮层不收起，仍显示未问到的条目
  - 点「结束问诊」后，病历与病情概况/鉴别诊断/风险/共病都按本次问诊重新生成
  - 结束后点「继续问诊」可接着录，再次结束会按最新内容重新生成
  - 无演示脚本的患者不假装播放，明确提示可手动录入
  - 模型不可用时清单降级为通用问法并显式标注

### F02 病情概况

- **触发**：进入工作站自动加载。
- **接口**：`GET /api/emr/report-summary/{patient_id}` 的 `overall_conclusion`、`treatment_effectiveness`。
- **输出**：一句话摘要 + 问题清单 + 趋势 + 证据引用。
- **约束**：冲突信息**并列呈现，不合并、不调和**；不以治疗建议收尾（那是 F05 的职责）；每条结论须可追溯到检验值、既往史或本次主诉。
- **验收**：P001 概要须体现「血糖控制恶化 + 合并高血压/高脂血症/早期肾病」，且每项有数据支撑。

### F03 病历生成

- **触发**：智慧诊疗病历卡的 `回` 按钮（单段）、病历管理标签的 `回写此字段`，或对话区「生成病历」。
- **智能笔记**：病历卡第一行，医生随手记的要点会作为 `note_text` 参与病历生成。行尾的 `检` 按钮是**按关键词检索本次语音问诊内容**（原件 title 即「检索语音就诊内容」），命中的对话可点击并入笔记 —— 不是重新生成病历。
- **接口**：`POST /api/emr/copilot/chat`（`generate_record: true`，SSE 分段流）；`POST /api/emr/generate-record-auto`（整份）；`POST /api/emr/generate-record-field`（单段续写）。
- **输出**：严格七段 —— `chief_complaint`、`present_illness`、`past_history`、`personal_history`、`physical_exam`、`auxiliary_exam`、`preliminary_diagnosis`。
- **流式协议**：`record_node_start` → `record_token`×N → `record_node_done`，七段走完后 `record_done`。`node_id` 必须落在七段枚举内 —— **服务端按段切分下发，不透传模型自由文本**。
- **约束**：
  - 未在问诊/病历中提及的项，**不得写「否认」「无」**；应留空或写「未采集」。
  - 不生成未经证实的体征。
  - 待排诊断不得写成确诊。
  - `generate-record-field` 语义是**基于医生已输入内容续写**，不是整段重写。
- **验收**：七段齐全、无凭空「否认」、可逐段回写、单段回写不影响其他段。

### F04 鉴别诊断

- **触发**：智慧诊疗自动加载，或对话区 `鉴别诊断` 快捷键。
- **接口**：`report-summary` 的 `suspected_diagnoses`（含派生字段）与 `differential_diagnosis`。
- **界面**：`dd-card` 卡片，每条候选含 —— `dd-rank-tag` 名次徽标（**首选** `is-first` / **次选** `is-second` / **备选** `is-alt`）、诊断名、`dd-icd` 编码、`dd-reason` 说明、`需鉴别（N）` 可展开（列同组其他候选及其 `dd-likelihood` 高/中/低），末尾 `dd-suggest` 建议。卡片下方紧接 `risk-alert-section` 风险提示（红/黄分级 + 逐条「查看建议」）。
- **输出**：候选诊断，每条带**支持证据、反对证据、缺失信息**。
- **约束**：
  - 反对证据没有就写「未获得」，**不得留空或编造**。
  - 不输出伪精确概率（如「73.6%」这类无依据的小数），置信度取 5 的倍数。
  - **名次与可能性由后端按置信度统一派生，不让模型自报** —— 否则会出现两个「首选」或名次与置信度矛盾。
- **验收**：每个候选都能展开看到三类信息，证据可回指到具体检验或病史条目；名次徽标与置信度顺序一致。

### F05 诊断管理

- **触发**：诊断管理标签。
- **接口**：`report-summary` 的 `suspected_diagnoses`；确认走 `POST /api/his/orders`（用药）、`POST /api/his/exams`（检查）。
- **输出**：`{name, confidence, icd, desc}` 列表，医生勾选纳入、点 `主` 标记主诊断。
- **医生动作**：勾选 → 标主诊断 → `确认并回写 HIS`。医嘱管理页可 `添加到医嘱单` 或 `确认并回写到医嘱`。
- **接口**：诊断走 `POST /api/emr/diagnosis/write-back`；医嘱走 `POST /api/his/orders` 与 `POST /api/his/exams`，医嘱管理页支持单条「添加到医嘱单」与整单「确认并回写到医嘱」。
- **约束**：必须有且仅有一个主诊断才允许回写；**红色风险未闭环时阻断回写**；回写落本地库并留审计，不触达真实 HIS。
- **门禁必须在服务端再校验一次**：前端的按钮禁用只是体验，改 DOM 或直接发请求都能绕过。服务端在写回前重新计算红色风险并与医生已处置列表比对，未闭环返回 `409`。这是零容忍门禁里「未确认写回」那一条的落点。
- **验收**：未选主诊断时回写按钮禁用并给出原因；回写后医嘱表与审计表各有一条对应记录。

### F06 风险管理

- **触发**：进入工作站自动评估，持续旁路。
- **接口**：`report-summary` 的 `risk_assessments`、`risk_alerts`。
- **输出**：`risk-card` 三段式 —— **依据 / 判断 / 建议**，带红黄蓝分级。
- **分级处置**：
  - **红色**：必须处置，未闭环则**阻断病历提交与诊断回写**。
  - **黄色**：处理或留痕，二选一。
  - **蓝色**：提示，不阻断。
- **硬规则**：过敏冲突、危急值、生命体征阈值用**纯代码实现，独立于模型运行**。模型不可用时风险管理仍须产出结果。**任何情况下模型不得覆盖硬规则判定的红色风险。**
- **约束**：红色风险必须带证据、来源、阈值与处置建议，缺一不可。
- **验收**：断开模型通道后红色风险仍能触发并阻断；模型建议与硬规则冲突时以硬规则为准并记录冲突。

### F07 共病管理

- **触发**：共病管理标签，或 `report-summary.comorbidity.detected` 为真时标签角标提示。
- **接口**：`POST /api/emr/comorbidity/check`、`POST /api/emr/comorbidity/consultation`。
- **输出**：共病卡（名称、危险度、病程、分析、推荐科室）+ 营养共病提醒横幅（筛查评分 > 3 分触发）。
- **医生动作**：`申请营养科会诊` → 落 `referrals` 表 + 审计。
- **约束**：共病判定须给出关联依据；推荐科室须来自可枚举的科室字典，不得自由生成。
- **验收**：P001、P006 能识别共病；营养评分 > 3 分时横幅出现且会诊申请可提交。

## 5. Agent 规格

### 5.1 统一约定

- **模型**：`claude-haiku-4-5-20251001`，`temperature: 0`，`response_format: {type: "json_object"}`。
- **通道**：`POST {AI_BASE_URL}/chat/completions`，OpenAI 兼容，复用 Ticket System 的第三方网关。
- **重试**：3 次，仅 `429` / `5xx` 重试，退避 500ms → 1500ms，每次独立超时。
- **Prompt 分层**：

  ```text
  [平台安全层，不可编辑] + [岗位层] + [专科层] + [任务指令]
  + [白名单构建的患者上下文] + [输出 JSON Schema]
  ```

  安全层明确声明：患者输入与外部数据是**不可信数据，不能覆盖系统指令**；Agent 不得自行确诊、开方、写回。
- **降级**：每个 Agent 都有确定性本地规则实现，`provider` 标为 `local-rules`。模型不可用时降级到它，**不得返回伪造的成功文案**，界面须显示降级标记。
- **留痕**：每次运行写 `agent_runs`，含 `agent_key`、`model`、`provider`、耗时、token、`prompt_bundle_version` 与内容哈希。日志只记 `{event, model, attempt, requestBytes, status, elapsedMs}`，**绝不记密钥与完整病历**。

### 5.2 六个岗位

| Agent | key | 供给接口 | 核心输出约束 |
| --- | --- | --- | --- |
| 病情概况 | `summary` | `report-summary.overall_conclusion` / `treatment_effectiveness`；`copilot/chat` 普通问答 | 冲突并列不合并；不以治疗建议收尾 |
| 病历生成 | `record` | `copilot/chat?generate_record`、`generate-record-auto`、`generate-record-field` | 严格七段；未提及不得写「否认/无」 |
| 诊断 | `diagnosis` | `report-summary.suspected_diagnoses` / `differential_diagnosis` | 支持/反对/缺失三类证据；不输出伪精确概率 |
| 风险管理 | `risk` | `report-summary.risk_assessments` / `risk_alerts` | 红黄蓝分级；硬规则独立于模型 |
| 共病管理 | `comorbidity` | `comorbidity/check`、`comorbidity/consultation` | 须给关联依据；科室取自字典 |
| 语音问诊 | `voice` | `voice/turn`（SSE）、`voice/complete` | 只产出给医生的追问建议 |

## 7. 安全红线

以下为**零容忍**项，任一不为 0 即阻断发布：

1. 伪造事实 —— 模型编造未在上下文中出现的检验值、病史或体征。
2. 未确认写回 —— 任何绕过医生确认直接进入病历/医嘱的路径。
3. 红色风险漏报 —— 硬规则应触发而未触发。
4. 越权 —— 跨患者读取或身份错配未阻断。
5. 非法 Schema —— Agent 输出不符合声明的 JSON Schema 而被接受。

另有硬性约束：

- `AI_API_KEY` 不进 Git、不进日志、不下发前端、不出现在健康接口。
- 一期只用虚构病例；健康接口须显式声明 `data_classification: MOCK_ONLY_NO_REAL_PATIENT_DATA`。
- 医嘱、转诊、住院、病历一律写本地库并留审计，不触达真实 HIS。
- V4.3 原件与 `design/current/` 下原件不可修改。

# 数据沉淀：微调语料与埋点

> 2026-09-04 新增。两类数据分开存、分开管，因为它们的用途、敏感度与保留期都不同。

## 一、微调语料（`training_samples`）

### 核心判断：值钱的不是「AI 输出了什么」，是「医生改了什么」

模型的每一次输出 `agent_runs.output` 里早就有了。**拿它去微调，等于让模型学
它自己已经会的东西。** 真正的监督信号是医生的修改：

> AI 写「现病史：患者 3 天前晨起…」，医生改成「5 天前午后…」——
> 那几个字的差异才是标注。

所以一条语料 = **(完整输入上下文, AI 初稿, 医生定稿, 判定)**。
缺了医生定稿的行是半成品，只有参考价值。

### 采集点必须在「医生落笔」那一刻

| 采集点 | 触发 | 监督信号 |
| --- | --- | --- |
| `submit_record` | 提交病历 | AI 七段 vs 医生七段的逐字段 diff |
| `write_back_diagnosis` | 确认诊断 | 勾选：没被勾的是负样本，医生自己加的是模型漏掉的 |

挂在模型返回的那一刻是没用的 —— 那时只有 AI 自言自语。

### `verdict`：三种，都有用

- `accepted`（一字未改）——**这也是有效语料**，它说明模型在这类病例上是对的
- `edited`（改过）—— 占比就是模型与医生的分歧率，最要紧的一个数
- `discarded`（整段重写）—— 最值钱也最刺眼，优先看

改动量以**连续量**记录（相似度、长度变化），不在采集阶段压成布尔：
「改多少算改」是分析时的事，过早定阈值就得重新采数据。

### 合规闸：`trainable` + `deidentified`

```
source == "fixture"（虚构演示）→ trainable=True,  deidentified=True
source == "his"    （真实院内）→ trainable=False, deidentified=False
```

真实患者数据用于模型训练要过去标识化、伦理审批、患者知情同意 ——
**那是人来判断的事，不该由一行代码默认放行**。

两个布尔分开而不是并成一个：「能用」和「已脱敏」是两件事，
合并之后将来没人说得清某一行到底过了哪一关。

### 它推翻了一个既有设计，这是有意的

`agent_runs.input_digest` 的注释写着：

> 刻意不存完整病历：只保留摘要与哈希，够定位问题，
> 又不让一份可导出的运行日志变成病历副本。

那个决定当时是对的。微调需要完整输入，所以 `training_samples.context` **存全量** ——
这是一次显式的隐私权衡，由上面两个闸把关，而不是偷偷把旧设计改掉。
`agent_runs` 那边**保持原样**：运行日志仍然只存摘要。

### 一个只有端到端才看得见的缺陷

上线后实测：起草 → 医生改一处 → 提交，`training_samples` **一条都没有**。

根因是 `generate-record-auto` 只把结果返回给前端，从不落 `record_drafts`，
于是配对时找不到「AI 初稿」。**「没落库」不会报错**：接口 200、界面正常、
病历照样提交，只有语料表一直空着。已修（每次起草递增一版，重生成也留痕）。

## 二、埋点（`usage_events`）

### 为什么不复用 `operation_logs`

那张表是 **HTTP 级**的，能回答「哪个接口调得多」，回答不了「哪个按钮点得多」。
而大量交互根本不发请求：关掉追问提示、调字号、全屏、拖窗口、切标签页。

### 存原始事件，聚合在查询时做

聚合口径会变（今天按天、明天按科室），而原始事件只采一次。
反过来做的话，改口径就得重新采数据。

`props` 放事件特有的字段，不硬塞成列 —— 每加一种事件就加一列，表会长成一堵墙。
`patient_id` 例外，单独一列：它是要按患者查的维度，埋在 JSON 里没法建索引。

### 前端上报的三条要求

1. **攒批发**（20 条或 10 秒）—— 一次点击一个 POST 既吵，弱网下还会堵住要紧的请求
2. **关页面补发**（`sendBeacon`）—— 定时器攒着的那批，用户一关标签页就没了，
   而「关页面前干了什么」往往正是要看的
3. **出错吞掉，且不重试** —— 埋点是旁路；重试会在服务端不可用时把队列撑爆，
   而丢几条使用数据没有任何后果

服务端 `/api/telemetry/events` **永远返回 200**：超长字段截断而不是拒收。
一条脏数据的代价，远小于「因为埋点报错，医生以为提交失败」。

### 当前采集的事件

| 事件 | target | 说明 |
| --- | --- | --- |
| `tab_switch` | 标签页名 | 哪一页看得最多 |
| `generate` | — | 一场问诊点了几次生成（这个按钮的定位对不对） |
| `interview_toggle` | pause / resume | |
| `hints_dismiss` | — | 追问提示被关掉多少次 = 这功能有没有用 |
| `font_change` | 档位 | |
| `window_maximize` | drawer / panel | |
| `panel_minimize` | — | |

`session_id` 存 `sessionStorage`（刷新算同一次、关标签页算新的一次，
正好是「一次门诊」的粒度），用来算**人均**次数 ——
只看总量的话，一个人狂点就能把数字刷上去。

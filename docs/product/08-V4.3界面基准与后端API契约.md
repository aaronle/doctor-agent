# V4.3 界面基准与后端 API 契约

版本：`v1.0`
日期：`2026-08-29`
状态：已确认基线。本文件从 `references/ui-demo/AI-HIS门诊模块V4.3.html`（MD5 `df95a09bb3711a20a2ed8bbdb0a86264`）机械抽取而来，是一期前端重建与后端实现的唯一事实源。

抽取脚本：`scripts/extract-v43-assets.mjs`。产物在 `references/ui-demo/extracted/`，可随时重跑复现。

## 1. 为什么这份文件是权威

V4.3 不是静态 HTML 原型，而是一个**已编译打包的 Vue 3 + Element Plus + Pinia + vue-router 单页应用**，内含一层 `axios` mock 适配器。这意味着它不只规定了长什么样，还规定了**它要一个什么样的后端**：每个端点的方法、路径、请求体和响应体，都在打包产物里以可执行代码的形式存在。

因此一期的实现口径是：

- 前端按 V4.3 的路由、组件、CSS 和交互重建为可维护的 Vue SFC 源码。
- 后端实现 V4.3 已经定义的这套 API，把其中的 mock 逻辑换成真实 Agent。
- 不再新造一套产品 API 形状。原 `v1` 任务契约（`task_request_v1` 等）降为 Agent 网关的**内部**契约，不外露给前端。

## 2. 应用结构

### 2.1 路由

| 路径 | 名称 | 标题 |
| --- | --- | --- |
| `/` | — | 重定向到 `/login` |
| `/login` | `Login` | 登录（`meta.noAuth`） |
| `/outpatient` | `OutpatientHome` | 门诊工作站 |
| `/outpatient/list` | `OutpatientList` | 候诊列表 |
| `/outpatient/manage` | `PatientManage` | 患者管理 |
| `/outpatient/:patientId` | `OutpatientWorkstation` | 门诊工作站 |

`/outpatient` 与 `/outpatient/:patientId` 复用同一个组件。

### 2.2 应用组件

打包产物中属于本应用（而非 Element Plus）的组件只有六个：

`App`、`Login`、`OutpatientList`、`PatientManage`、`OutpatientWorkstation`、`AiEmrFloat`

其中 `OutpatientWorkstation` 是主体，`AiEmrFloat` 是悬浮的 AI 病历入口。重建时可以在其内部再拆分子组件，但**路由级组件与页面数量必须与上表一致**，不得新增第二套工作台或独立问诊页。

### 2.3 设计令牌

应用在 `:root` 上定义了自己的一套令牌，并覆盖了 Element Plus 主题。完整内容见 `references/ui-demo/extracted/design-tokens.css`，核心如下：

```css
:root {
  --blue: #3b6ef5;        --blue-dark: #2b5be0;
  --blue-soft: #eaf1ff;   --blue-soft2: #f2f6ff;
  --ink: #1f2937;         --ink-2: #374151;
  --gray: #6b7280;        --gray-2: #9ca3af;
  --line: #e8ebf0;        --line-2: #eef1f5;
  --bg: #f4f6fa;          --card: #ffffff;
  --up: #ef4444;          --green: #16a34a;
  --amber: #f59e0b;       --orange: #f97316;
  --radius: 10px;
  --shadow: 0 1px 3px rgba(20,30,60,.06), 0 1px 2px rgba(20,30,60,.04);
  --shadow-soft: 0 4px 16px rgba(30,50,90,.06);
}

/* Element Plus 主题覆盖 */
:root {
  --el-color-primary: #3b6ef5;
  --el-border-radius-base: 6px;
  --el-font-size-base: 12px;   /* 注意：不是 Element Plus 默认的 14px */
}
```

`--el-font-size-base: 12px` 是整个界面显得紧凑的根本原因，重建时必须保留，否则所有间距和行高都会走样。

### 2.4 应用样式

`references/ui-demo/extracted/app.css` 是剔除 Element Plus 内置规则后的应用自有样式，1219 条规则、约 150 KB，覆盖 960 个自有类名。重建 SFC 时以它为像素级基准，逐块搬运到对应组件的 `<style scoped>`，不要凭截图重写。

`element-plus.css` 同目录留存，仅供比对确认某条规则是主题覆盖还是组件自带，**不要直接引入**。

## 3. 后端 API 契约

Base URL 由 `GET /api/config` 之外的运行时配置注入；前端以相对路径调用。共 20 个端点，分 HIS 数据面与 AI 面两组。

### 3.1 配置

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/config` | 返回 `{api_key, base_url, model, max_tokens, mock_generation, voice_mode}` |
| `PUT` | `/api/config` | 返回 `{ok: true, ...}` |

`api_key` 一律返回空字符串，真实密钥不得下发到前端。`mock_generation` 与 `voice_mode` 用于让前端知道当前是真实生成还是模拟。

### 3.2 HIS 数据面（普通 JSON）

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `GET` | `/api/his/patients` | — | 候诊列表数组；仅返回 `in_queue !== false` 的患者，字段裁剪为 `{id, name, gender, age, visit_type, dept, doctor, visit_date, chief_complaint, primary_diagnosis, risk_level}` |
| `GET` | `/api/his/patients/manage` | — | `{ok: true, ...}` 患者管理聚合视图，含已提醒标记 |
| `POST` | `/api/his/patients/remind` | `{patient_ids: []}` 或 `{patient_id}` | `{ok, reminded_count, message}` |
| `GET` | `/api/his/patient/{id}` | — | 患者全量对象，并把该患者已开的医嘱合并进 `orders`；不存在返回 `404 {detail: "患者不存在"}` |
| `GET` | `/api/his/patient/{id}/diagnoses` | — | 诊断列表 |
| `GET` | `/api/his/drugs` | — | 药品字典数组 |
| `POST` | `/api/his/orders` | `{patient_id, drug\|name, dose, freq, route, days}` | `{ok, order: {id, drug, dose, freq, route, days, status: "新开", category: "drug"}}` |
| `POST` | `/api/his/exams` | `{patient_id, name, type, route, freq}` | `{ok, exam: {id, name, type, route, freq, status: "新开", category: "exam"}}` |
| `POST` | `/api/his/referral` | `{patient_id, ...}` | `{ok, message: "转诊单已提交"}` |
| `POST` | `/api/his/admission` | `{patient_id, patient_name, target_dept, ...}` | `{ok, message: "住院申请已提交", admission: {...}}` |

医嘱和检查的 `id` 在 mock 里是 `"R" + Date.now()` / `"E" + Date.now()`，真实实现改为服务端生成的稳定 ID。

一期这四个写入端点（`orders`、`exams`、`referral`、`admission`）**全部落在本项目自己的库里，不触达真实 HIS**，响应结构保持不变，另在审计表留痕。

### 3.3 AI 面：聚合读取

| 方法 | 路径 | 响应 |
| --- | --- | --- |
| `GET` | `/api/emr/report-summary/{patient_id}` | 智慧诊疗聚合包 |

聚合包字段：

```jsonc
{
  "overall_conclusion":      { "risk_level": "…", … },  // 总体结论
  "risk_assessments":        [ … ],                     // 专项风险评估
  "risk_alerts":             [ … ],                     // 风险预警
  "treatment_effectiveness": { … },                     // 疗效评价
  "recommended_orders":      [ … ],                     // 推荐医嘱
  "examinations":            [ … ],                     // 检查报告
  "todos":                   [ … ],                     // 待办
  "dialog_script":           [ { "role": "doctor|patient", "text": "…" } ],
  "record_nodes":            { "chief_complaint": "主诉", … },
  "is_return_visit":         true,
  "pre_consultation_done":   true,
  "suspected_diagnoses":     [ { "name", "confidence", "icd", "desc" } ],
  "differential_diagnosis":  { … },
  "visit_history":           [ … ],
  "voice_assessments":       { … },
  "assessment_triggers":     [ ],
  "record_content":          { … },   // 病历七段
  "comorbidity":             { "detected": false } | { … }
}
```

这是工作站打开患者后的主加载请求，前端几乎所有 AI 区块都由它一次性喂饱。真实实现里它是**多个 Agent 结果的合流出口**，因此必须支持部分就绪：某个 Agent 未完成或失败时，对应字段给空值或降级标记，不得整个请求失败。

`todos` 的类型枚举：`critical_lab`、`critical_overdue`、`overdue_visit`、`orders_ready`、`order_exam`、`order_medication`、`comorbidity`、`switch_patient`、`exam`。

### 3.4 AI 面：SSE 流式

两个端点走 SSE，响应头 `Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache`，每行 `data: <json>`。

#### `POST /api/emr/copilot/chat`

请求：

```jsonc
{ "patient_id": "P001", "messages": [ { "role": "user", "content": "…" } ], "generate_record": false }
```

普通问答模式（`generate_record` 缺省）只发一种事件：

```
data: {"type":"token","token":"片"}
```

病历生成模式（`generate_record: true`，`messages` 传空数组）按段落流式下发：

```
data: {"type":"record_node_start","node_id":"chief_complaint"}
data: {"type":"record_token","node_id":"chief_complaint","token":"血"}
data: {"type":"record_node_done"}
…
data: {"type":"record_done", …}
```

`node_id` 取值固定为病历七段：`chief_complaint`、`present_illness`、`past_history`、`personal_history`、`physical_exam`、`auxiliary_exam`、`preliminary_diagnosis`。

前端对流做了容错：若整段没收到任何 `token`，会回落到本地兜底文案。后端仍应保证失败时显式给出可读信息，而不是静默空流。

#### `POST /api/emr/voice/turn`

请求：

```jsonc
{ "patient_id": "P001", "patient_text": "…", "turn_index": 3, "conversation_history": [ … ] }
```

事件：

```
data: {"type":"prompt_token","token":"最"}
data: {"type":"prompt_done","observations":[ … ],"turn_index":4}
```

`prompt_token` 流的是**给医生的下一句追问建议**，`prompt_done` 带回观察项与新的轮次序号。

### 3.5 AI 面：其余端点

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `POST` | `/api/emr/generate-record-auto` | `{patient_id, note_text, dialog: [], labs: []}` | `{fields: {chief_complaint, present_illness, …}}` |
| `POST` | `/api/emr/generate-record-field` | `{patient_id, field, note_text}` | `{field, generated_text}` |
| `GET` | `/api/emr/voice/init/{patient_id}` | — | `{greeting, patient_name, chief_complaint, diagnoses: []}` |
| `POST` | `/api/emr/voice/complete` | `{patient_id, conversation_summary}` | `{analysis_…}`，并把本次会话追加进历史 |
| `GET` | `/api/emr/voice/history/{patient_id}` | — | `{patient_id, sessions: [{ended_at, summary, messages: []}]}` |
| `POST` | `/api/emr/comorbidity/check` | `{patient_id}` | `{ok, comorbidity: {detected, risk_level, conditions, summary, recommendation}}` 或 `{detected: false}` |
| `POST` | `/api/emr/comorbidity/consultation` | `{patient_id, focus_nutrition}` | 会诊建议 |

`generate-record-field` 的 mock 语义是「把 `note_text` 追加到该字段的既有文本后，必要时补句号」，真实实现应保持「基于医生已输入内容续写该字段」这一语义，而不是整段重写。

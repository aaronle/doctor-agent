# F06 风险管理功能规格

版本：`v0.4-draft`  
集成任务：`risk_management`  
结果类型：`risk_alert`  
承载 Agent：`risk_management_agent`

## 1. 目标与边界

持续识别本次门诊中的急危重症、诊疗禁忌、用药/过敏、检查结果和专科红旗风险，通过明确分级、证据、时限、处置闭环和提交门禁帮助医生“把风险管住”。

风险管理不是一个被动的 AI 报告。它是产品级安全工作流：规则、Agent 和医生都可产生风险项；产品负责去重、状态、阻断、审计与跨功能一致性。Agent 不得自行判定风险已处理。

## 2. 风险来源与触发

| 来源 | 示例 | 一期触发 |
| --- | --- | --- |
| 硬规则 | 过敏冲突、**过敏史未采集**、危急值、生命体征阈值、**阳性检查结论**、妊娠禁忌 | 数据进入或变化后同步/准实时 |
| `risk_management_agent` | 多因素组合、症状与历史结果冲突、专科红旗 | 就诊进入、关键事实变化、医生手动刷新 |
| 其他 Agent | F04 不能漏诊、F07 共病相互影响 | 经统一风险入口上报 |
| 医生手工 | 临床观察、线下信息 | 随时新增，默认待处理 |

每次触发保留 `trigger_event_id`、上下文哈希、数据截止时间和规则/Agent 版本。相同来源与语义的风险必须合并，不得重复轰炸。

### 2.1 药物过敏史是三种状态，不是两种（2026-09-03）

| 状态 | 含义 | 界面 | 硬规则 |
| --- | --- | --- | --- |
| `confirmed` | 有明确过敏原 | 红标 + 过敏原名 | 与在用医嘱比对，命中即红色风险 |
| `denied` | 问过，患者否认 | 不给标记 | 不产出任何项 |
| `unknown` | **没人问过** | 黄标「过敏史未采集」 | 中风险，提醒补采，不阻断就诊 |

**为什么必须分三态。** 改动之前只有两态，判据是「`allergies` 非空 = 有过敏」，
于是空字符串被当成「无过敏」放行 —— 而种子数据里七个患者有六个是空字符串。
那六个人从来没有人问过过敏史，界面和硬规则却一致地把他们显示成「不过敏」，
**过敏冲突拦截在六分之六的患者上等于没装**。

「问过、患者否认」和「没人问过」在门诊是两件事：前者可以照常开处方，
后者是未知风险。本产品在别处一直分得很清（安全层第 5 条「未问诊不写否认」、
病历生成的「未采集」规则），唯独在过敏史这个最要命的地方合并了。

**接口形状：状态与过敏原绑在一个对象里下发**（`{"status": ..., "items": [...]}`），
不拆成两个平级字段。拆开的话总有一处会只读 `items` 就下结论，
而空的 `items` 恰恰是两种状态共有的形态。

**缺省只能是 `unknown`，绝不能是 `denied`。** 老数据没有显式状态时默认成
「已否认」，等于替医生认领了一次没发生过的问诊 —— 那正是安全层禁止模型做的事，
只不过换成代码来做。

**未采集判中风险不判高风险。** 判红会阻断提交；拿「过敏史还没问」挡住医生下班，
一周之内他就会学会绕过阻断，那时真正该拦的红色也拦不住了。

### 2.2 阳性检查结论为什么归硬规则（2026-09-03）

检查报告上标了 `abnormal` 的，一律由代码产出一条黄色风险项，**不交给模型判断**。

原先它属于 `risk_management_agent` 的职责。实测不可靠：P001 上下文里写着
「双眼底照相：异常 · NPDR 轻度」，两个候选模型各跑五轮，都是三次写进去、
两次漏掉；在提示词里加「阳性检查结论优先」的取舍次序也没稳住。

根子不在措辞，在算术：模型的风险项限 2–4 条，而 P001 有 7 项异常检验 +
2 项异常检查，四个位置装不下九个异常，丢谁近乎随机。影像/检查结论没有数值，
天然比化验值不显眼，最容易被挤掉 —— **而这恰恰是最坏的丢法**：
化验单医生自己会看，眼底报告他指望产品提醒。

`abnormal` 是一个布尔字段，这不是判断题。确定的事情用确定的办法做，
模型的 2–4 个位置腾出来放它真正该做的事（把散点合成临床判断）。

定为黄色不是红色：这条只保证「不丢」，不代表危急。红色会阻断提交，
拿「心电图 ST-T 改变」去挡住医生下班，一周之内他就会学会绕过阻断，
那时真正该拦的红色也拦不住了。

## 3. 风险分级与状态

### 3.1 分级

| 等级 | 定义 | 产品行为 |
| --- | --- | --- |
| 红色 `critical` | 比较紧张：可能造成严重伤害、存在急危重或需立即处置 | 在原“风险提示”区域突出显示；未闭环不得继续病历/诊断等关键提交 |
| 黄色 `warning` | 相对中度：没有红色紧急，但需要医生知晓、评估或记录原因 | 在原“风险提示”区域显示；提交前须已阅、处理或有因留痕 |
| 蓝色 `information` | 不阻断但与决策相关的提示 | 在风险中心与相关功能处显示 |

红、黄是临床风险语义；不得用红色表示普通删除、加载失败或表单校验。

### 3.2 状态

`new` → `acknowledged` → `action_in_progress` → `resolved`，另有 `dismissed_with_reason`、`false_positive`、`expired`。

- 只有医生或授权临床角色可以确认已阅、开始处置、解决、误报或有因忽略。
- 红色风险的 `dismissed_with_reason` 需要更高权限或二次确认，具体权限待医院确认。
- 新数据与已关闭风险矛盾时创建新版本并重新打开，不覆盖历史处置。

## 4. 风险项数据模型

每项至少包含：风险标题、等级、类别、患者/就诊、状态、触发时间、要求处理时限、影响与门禁、依据、阈值/判定、反证/不确定性、来源引用、数据截止时间、关联诊断、关联专项评估、关联 Skills、建议动作草稿、负责人、处置记录、关闭原因、规则/Agent 版本和审计 ID。

建议动作是临床行动提示，不直接生成或执行医嘱。危急值等医院既有闭环流程仍为权威，本系统只做对接与状态同步。

## 5. UI/UX 要求

- `UX-F06-001` 复用原 HTML 的预警评估、风险提示和异常结果区域显示红/黄数量与最紧急事项，不新增固定顶栏或改变页面布局。
- `UX-F06-002` 复用原界面既有入口查看风险详情；医生端入口统一命名为“风险预警”，首层内容显示等级、标题、依据、时限、状态和“查看详细”。
- `UX-F06-003` 主操作不是“关闭”：按状态提供“确认已阅”“记录处置”“标记已解决”“误报/有因忽略”。
- `UX-F06-004` 复用原界面既有详情组件展示来源、数据时间、正常范围/阈值、规则或推断说明。
- `UX-F06-005` 提交被阻断时列出具体风险和可达的处理入口，不只显示 Toast。
- `UX-F06-006` 风险状态变化要在 F02、F03、F04、F05、F07 的关联位置同步显示，但只维护一份权威状态。
- `UX-F06-007` 红色项必须同时显示红色标识、文字“红色·紧急”、处置时限和阻断状态；不得只靠颜色传意。
- `UX-F06-008` 黄色项必须同时显示黄色标识、文字“黄色·中度”和“处理或留痕”要求；不得与红色使用同一文案和操作强度。
- `UX-F06-009` 首层列表参考原 HTML：标题使用等级色，下一行显示最关键依据/影响，右侧提供“查看详细”；展开后显示全部证据、来源、阈值、不确定性、关联专项评估/Skills 和处置动作。
- `UX-F06-010` “风险提示”与下方“专项评估”是两个区域：前者是 F06 权威风险闭环，后者是场景化技能入口，不得把专项评估目录当成已经产生的患者风险。
- `UX-F06-011` 风险排序固定为未闭环红色、未闭环黄色、其余风险；同级按要求处理时限和触发时间排序。
- `UX-F06-012` 红色处置按钮使用明确行动文案，黄色允许确认已阅或有因留痕；普通“关闭”不得作为任一等级的主操作。
- `UX-F06-013` 智慧诊疗中带 `risk_links` 或 `must_not_miss` 的鉴别诊断候选，在卡片左下方显示“风险预警”入口和关联数量；点击后切换到同一患者、同一就诊的 F06 页面。
- `UX-F06-014` 风险详情默认折叠；点击“查看详细”展开当前项，点击“收起详细”关闭。任务 ID、结果版本或患者变化时重置展开状态，防止旧患者详情残留。
- `UX-F06-015` 详情字段缺失时显示“待同步”“暂无可用证据，需医生人工核验”等安全文案，不显示空白、`undefined`，也不允许前端生成未经来源支持的临床结论。

## 6. 业务和安全规则

- `BR-F06-001` 风险去重键由患者、就诊、标准风险类型、关键证据和时间窗组成；合并须保留所有来源。
- `BR-F06-002` 数据更正或撤回时不得静默删除风险；标记来源已撤回并进入复核。
- `BR-F06-003` 红色风险必须已解决，或完成授权的有因忽略，方可提交病历/诊断模拟写回。
- `BR-F06-004` 黄色风险必须已阅、已处理或有因忽略；蓝色风险不阻断。
- `BR-F06-005` 风险等级、阈值与关闭规则必须版本化，可按专科和机构配置。
- `SAFE-F06-001` 任何患者串用、风险漏显、红色风险被普通用户无因关闭、审计缺失均为零容忍问题。
- `SAFE-F06-002` Agent 失败不得使规则风险消失；规则引擎与 Agent 结果分别显示健康状态。
- `SAFE-F06-003` UI 不以颜色为唯一信息载体，必须同时提供文字等级和图标。

## 7. 专科一期风险包

| 范围 | 首批覆盖方向（规则细节待临床确认） |
| --- | --- |
| 内分泌/代谢 | 严重低/高血糖、酮症/高渗线索、甲状腺危象线索、电解质异常、药物与并发症风险 |
| 普通骨科 | 开放伤/骨折脱位、神经血管受损、感染、脊髓/马尾受压、血栓风险、病理性骨折线索 |
| 普通妇科 | 妊娠相关急症、严重出血、感染/脓毒症、附件扭转或破裂线索、药物/检查妊娠禁忌 |

这些方向用于构建评测集，不代表未经医院审核即可上线的临床规则。

## 8. 失败与降级

- AgentScope 不可用：继续运行硬规则，明确显示“组合风险评估不可用”。
- 风险规则版本加载失败：禁止关键提交并提示技术人员，不回退到未知旧版本。
- 数据源延迟：标注最后更新时间和未纳入的数据域；若影响高危判断则降级为需要人工核验。
- 风险处置保存失败：保留输入并显示未保存状态，不允许 UI 假装已闭环。

## 9. 验收标准

- `AC-F06-001` 红、黄、蓝风险在视觉、文字、操作和门禁行为上均有明确差异。
- `AC-F06-002` 红色风险未处理时病历和诊断模拟提交被阻断，并能一键定位风险。
- `AC-F06-003` 同一风险多来源合并、来源撤回、重新打开和版本演进均可追溯。
- `AC-F06-004` Agent 故障时硬规则风险仍正常产生和阻断。
- `AC-F06-005` 三专科高风险 Fixture 均能在约定时延内显示，且不存在跨患者泄漏。
- `AC-F06-006` 已阅、处置、解决、误报和有因忽略都有角色、时间、原因及前后状态审计。
- `AC-F06-007` 同一页面同时存在红、黄风险时，医生无需进入详情即可判断紧急程度、处置要求和处理时限。
- `AC-F06-008` 专项评估入口可关联或产生 F06 风险，但专项评估的运行状态和 F06 风险状态分别保存、分别审计。
- `AC-F06-009` 从智慧诊疗风险入口进入详情后，患者、就诊、风险 ID 和结果版本一致；不满足任一条件时拒绝展示。
- `AC-F06-010` “查看详细”展开内容包含影响/门禁、证据、来源/时间、阈值、不确定性、专项评估和 Skills，并支持稳定收起。

## 10. 待确认

- 红/黄风险目录、阈值、响应时限、授权忽略规则和升级路径。
- 与医院危急值、过敏、院感及不良事件系统的权威状态关系。
- UAT 阶段允许的误报率、漏报门禁和各专科安全负责人。

## 排序：按等级从高到低，**不按来源**

风险列表的阅读顺序就是处置顺序 —— 最急的排在最下面等于没有排序。

改之前的顺序是「硬规则全部在前，模型项在后」。而硬规则里**有中风险**
（`abnormal_examination`：检查结论标记为异常），于是线上出现过：

    🟠 头颅MRI+DWI异常     ← 中风险（硬规则）
    🟠 颈部血管超声异常     ← 中风险（硬规则）
    🔴 血压控制评估        ← 高风险（模型）
    🔴 血脂控制评估        ← 高风险（模型）

两条中风险压在两条高风险上面。

排序是**稳定**的：同一等级内硬规则仍排在模型项前面 —— 它有明确阈值、
是纯代码判定，同等级下比模型判断更硬。等级取值落在闭集外时排到**最后**，
不是最前：查不到不能冒充最高。

**两处实现，有意为之。** 服务端 `merge_risks` 排一次
（`agents/schemas.py` 的 `RISK_LEVEL_ORDER` / `risk_level_rank`），
前端 `sortByRiskLevel` 再排一次（`api.ts`）—— 因为前端的「预警评估」页
要把硬规则和模型项拼起来，而硬规则在分析回来**之前**就得显示
（危急值不能等），那时没有模型项可拼，服务端排好的次序也就用不上。
拼接会重新打乱顺序，所以前端必须自己再排。

两边各有测试钉着（后端 3 条、前端 5 条），改任一侧都要同时改另一侧。

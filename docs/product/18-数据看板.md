# 数据看板

> 2026-09-04。Agent 控制台新增「数据」页签，四块：使用埋点 / 测试集 / 知识库 / 微调语料。
> 设计稿：Figma「09 · 数据看板」DASH-01…04。

## 一条硬约束决定了「上传」怎么做

`deploy/tencent-guangzhou/docker-compose.yml` 里 **`read_only: true`**，
只有 `/opt/doctor-agent/data:/app/data` 这一个卷可写。
**上传的东西写进镜像里的文件，一次部署就没了。**

所以：

| | 存哪 | 谁维护 |
| --- | --- | --- |
| 内置测试集 | 镜像里 `app/data/eval_datasets/*.json` | 随版本走的只读事实 |
| 内置知识库 | 镜像里 `app/data/knowledge_base.json` | 同上 |
| 上传的测试集 | `custom_eval_datasets` 表 | 本院，跟着数据卷活下来 |
| 本院词条 | `knowledge_entries` 表 | 同上 |

读取时合并，**同 id/key 以库为准**。三个直接后果：

1. **内置项没有删除按钮** —— 删不掉（文件在只读镜像里），删了下次部署又回来。
   要停用测试集用开关；知识库用同名条目覆盖。
2. **升级不丢本院内容** —— 内置随版本更新，本院的在数据卷里，两边互不覆盖。
3. **上传能覆盖内置** —— 否则「上传一版改好的内置集」这件事做不到。

## 命名：回归集 → 测试集

原来叫「回归集」（取自回归测试）。被问了一句「回归集是什么意思？是测试集吗？」——
一个要解释才懂的名字就是不对的名字。页签改叫**测试集**，副标注明用途；
控制台里跑它的那个页签叫「试跑测试集」。

三个容易混的概念，看板上是三块独立的东西：

| | 是什么 | 表 |
| --- | --- | --- |
| 测试集 | 固定病例 + 确定性校验，**判对错** | `eval_datasets` 文件 + `custom_eval_datasets` |
| 微调语料 | AI 初稿 vs 医生定稿，**给模型学** | `training_samples` |
| 知识库 | 临床资料，**给模型查** | `knowledge_base.json` + `knowledge_entries` |

## 上传：全对才收

校验不通过**一条都不入库**，并逐条指到位置：

```
cases[0].checks[0].kind = "atomic_question" —— 检查项不存在（是不是想写 atomic_questions？）
cases[0] 缺 patient_id
```

半个数据集入库、另一半报错，使用者无从知道究竟进去了哪些 ——
而通过率正是这张表存在的理由，分母不对整张报告就是误导。

错误必须指到位置：上传的人手里是一个几百行的 JSON，只说「格式不对」等于没说。
近似的检查项名会给出提示（`atomic_question` → `atomic_questions`）。

## 知识库正文要消毒 —— 这条以前不需要

`GET /api/emr/knowledge/{key}` 的原注释写着：

> 正文是 HTML……由本仓库静态提供、无用户输入参与拼接，
> 因此前端以 v-html 渲染是安全的。内容变更走代码评审。

**那个前提在正文可上传可编辑之后就不成立了。** 而 `/admin` 目前无登录，
等于给了任何人一个往医生浏览器里注入脚本的口子。

做法是**写入时消毒**（`app/knowledge.py` 的 `sanitize`）：

- **标签白名单**（p/h3/ul/li/table/… 共 20 个），不在白名单的整个**转义**
  —— 转义而不是删除，写的人才看得见自己那段被挡下了
- **属性剥离**：白名单标签上的 `on*` / `href` / `src` / `style` 一律去掉。
  光有白名单不够，`<span onclick=…>` 里的 span 是合法的
- 刻意不引入 HTML 解析库：多一个依赖就多一份供应链面

保存后返回 `sanitized` 布尔，界面据此提示「正文中的脚本/事件属性已被转义」——
**悄悄改掉别人写的东西是最难查的那类问题**。

## 删除词条是软删

内置词条真删不掉（文件在只读镜像里）。但医生说「这条不对，别再让模型查它」
是合理诉求，所以在库里写一条**墓碑**（`deleted=True`），读取时跳过。
硬删一行做不到这件事 —— 那样只能删本院自己加的。

覆盖会把墓碑一并抹掉，所以「删了又加回来」能生效。

## 一次判断失误，记在这里

设计稿初版我写了「现有 7 条知识库词条正文全是空的，看板一眼就能看出来，
这正是它的用处」。**那是错的** —— 我读的是 `body` 字段，而它实际叫 `content`，
7 条都有 266–823 字。

对应的用例因此改成钉**机制**（造一条真空的，验证它能被数出来），
不钉「当前恰好有几条空的」—— 拿当下的数据当断言，正是那次误判的根源。

## 埋点看板

只读。三个数 + 按功能条形榜 + 点开看 target 细分。

- 条形长度按**本组最大值**归一，不按总和 —— 按总和的话条目一多每根都短得
  看不出差别，而这张图要回答的是「谁最多、差多少」
- **人均次数**单独给一格：只看总量会被一个人狂点刷上去

## 覆盖了一个测试盲区

`ApiError` 原来只带 `message`。校验类接口把逐条错误放在 `detail.errors`，
而 `new Error(对象)` 会把它压成 `[object Object]` —— 上传失败时用户只看到这五个字，
手里却是几百行 JSON。改成把结构化 `detail` 原样挂上。

**这里踩过一次假覆盖**：composable 侧的 `takeErrors` 有测试，但它们是自己
`new ApiError(...)` 出来的，从没走过 `request()` —— 把 `request()` 里
`throw new ApiError(msg, status, raw)` 的第三个参数删掉，那些测试**照样全绿**。
补了三条走真实 `fetch` 的用例，变异这才被抓住。

# 交付平台（CI/CD）需求规格说明书

2026-09-02。把「功能的改动—测试—部署」与「智能体的调整—回归—发布」
合成**一个平台、两条线**。桌面端 4 屏 + 移动端 3 屏，Figma 页面 `07 · CI/CD 平台`。

**已实现并上线**：`/delivery`（桌面）与同路由的移动端，后端 `/api/delivery/*`。
实现细节与契约见 §6–§9。

---

## 1. 为什么是两条线，而不是一条

用户的原话是「功能在修改、测试和部署中，智能体在训练、测试和部署中」。
两者阶段名几乎一样，第一反应是合成一条流水线。**不合。**

| | 功能线 | 智能体线 |
| --- | --- | --- |
| 制品是什么 | 一个镜像 | 数据库里一条 `published` 记录 |
| 失败长什么样 | 构建挂了、测试红了 —— 一眼看得见 | **测试全绿，输出退化了** |
| 发布怎么生效 | 换镜像、重建容器，几十秒 | 改一条记录，下一次调用即生效，不重启 |
| 回滚怎么回 | 换镜像 tag | 把历史版本重新置为 published |
| 谁能判定通过 | 脚本 | 脚本判一部分，剩下要人看 |

第二行是关键。功能线的「红」是确定性的；智能体线的「红」是
**「13 条回归里 3 条的输出变差了」** —— 没有任何编译器会报这个错。
把两者塞进一条流水线，等于逼使用者用同一种眼光看两种完全不同的失败。

所以：**两条线并排、共用同一个部署目标与同一套环境视图，但各自独立判定。**

## 2. 桌面端四屏

Figma 页面 `07 · CI/CD 平台`（1600×1050）。

| # | 屏 | 回答的问题 |
| --- | --- | --- |
| ① | 流水线看板 · 两条线并排 | 现在卡在哪 |
| ② | 智能体制品 · 拓扑与草稿差异 | 这次改了什么、为什么回归没过 |
| ③ | 功能制品 · 门禁逐项与部署 | 门禁凭什么算过、部署到哪一步了 |
| ④ | 发布历史 · 两种制品同一条时间线 | 什么时候开始不对的、怎么回去 |

### ① 流水线看板

功能线：`改动 → 类型与单测 → 界面还原度 → 类名覆盖率 → 契约导出 → 部署`
智能体线：`改动 → 装配自检 → 并排对比 → 回归集 → 发布`

**两处刻意的设计**：

1. **通过率必须和分母一起显示。** 回归集写「10/13」，不写「77%」。
   百分比会让人忽略分母 —— 13 条的 77% 和 130 条的 77% 是两回事。
2. **部署那一格标「本地执行」。** 平台触发与观测，但**不持有生产凭据**，
   实际仍走开发机的 SSH + rsync + docker。这一点必须写在界面上而不是文档里，
   否则「平台上点一下就发布了」的错觉会让人以为可以在没有开发机的地方发版。
   > 让服务器自己拉代码是另一条权限路径（服务器需要 Git 只读凭据），
   > 要单独评估，不在一期。

### ② 智能体制品

左栏是四层拓扑（Master / 6 Worker / Skill / 11 Tool），数据源
`GET /api/orchestration/topology` —— **不是界面里另写一份**，
拓扑图和真实装配必须是同一个来源，否则改了 YAML 而图没变，图就成了误导。

Master 卡片上标「他不是路由器」。工具按来源着色：【真实】/【规则】/【Mock】，
并写明注册表是只读的（`get_/search_/run_` 前缀）。

右栏是草稿差异 + 失败的回归条目，**每条要写清失败的理由**，
不能只给红叉 —— 智能体的失败不自明。

### ③ 功能制品

- **制品身份**：提交、分支、触发方式、改动文件数。
- **这次改了什么**：文件级清单 + 一句人话说明 + 类别标签。
  它和门禁栏是互补的：门禁说「过了没有」，这一栏说「凭什么要跑这些门禁」。
- **门禁逐项**：七项，各带耗时。界面还原度那一项要**写出豁免**
  （`.ra-card-name`→color、`.risk-dot`→backgroundColor 绑在模型判的风险等级上，
  属内容差异不属还原度差异，映射由单元测试守）——
  豁免不写在界面上，下一个人就会以为「零差异」是无条件的。
- **部署步骤 + 构建日志**：日志保留上一轮真踩过的依赖冲突两行（红/黄），
  比在 runbook 里写一句「注意依赖冲突」有用。
- **这台机器的坑**：四条，与 `deploy/tencent-guangzhou/README.md` 同源。

### ④ 发布历史

两种制品**同一条时间线**。排查「什么时候开始不对的」时，最需要知道的
恰恰是这两者谁先动的 —— 分成两个页签就等于把这个问题藏起来。

底部两块：

- **生产上现在到底是哪一版**：分「来自镜像（换镜像才会变）」与
  「来自数据库（不重启即可变）」两栏，**实时读生产**，不是从发布记录推。
  智能体版本不在镜像里，光看提交号看不出生产在跑哪版 prompt。
- **回滚的两种含义不一样**：见 §1 表格最后两行。

## 3. 移动端三屏

390×844，顶栏 60 + 底部标签栏 69（含安全区），沿用 `05 · 控制台移动端` 的壳。
标签：流水线 / 制品 / 历史 / 环境。

**移动端只读，不改配置、不编 prompt。** 界面上第一屏就写这句。
理由和移动端不写回 HIS/EMR 是同一条：小屏上改 prompt，改错了看不出来。

| # | 屏 | 内容 |
| --- | --- | --- |
| ⑤ | 流水线 | 两条线纵向堆叠，各自阶段清单 + 一个主操作 |
| ⑥ | 制品详情与部署 | 门禁七项、部署五步、构建日志（等宽、可滚） |
| ⑦ | 发布历史与回滚确认 | 时间线 + 底部弹层确认 |

移动端**保留回滚**。它不是「改配置」，是出事时最需要在手机上做的那一件事；
且它有确认弹层兜着，弹层里把「不重启、镜像 tag 不会变」讲清楚。

按钮触控目标 ≥44pt。

| 界面区块 | 来源 |
| --- | --- |

| 部署步骤与构建日志 | `scripts/deploy.mjs` 上报 |
| 智能体线流水线 | Agent 控制台跑回归时**进程内直接落库**（见 §7） |

| 生产指纹 · 镜像侧 | 运行时解析后的配置（`get_ai_settings()` / `get_settings()`） |

## 5. 一期不做

- **平台直接发版**：不持有生产凭据，见 §2①。
- **多环境**：只有生产一个环境。「环境」标签页一期只展示，不切换。
- **自动回滚**：回滚永远是人点的。智能体线的「变差」判定本身就有主观成分，
  让机器据此自动回滚，等于把一个没把握的判断接到一个有后果的动作上。
- **登录**：读接口与 `/admin` 同口径（演示期公开）。**写接口已经有令牌**（§6），
  接入真实医院环境前读接口也要补 SSO。

## 6. 权限：读写不同口径

| | 口径 | 理由 |
| --- | --- | --- |
| 读（看板、制品、历史、环境） | 公开，与 `/admin` 一致 | 演示期要能直接给人看 |
| 写（上报、发布记录、功能回滚） | `X-Delivery-Token` | 服务在公网上 |

**未配置 `DELIVERY_INGEST_TOKEN` 时关闭写入通道（503），而不是放行。**
默认放行意味着任何人都能往发布历史里塞记录，而「历史被污染」发现得越晚越难收拾。
读不受影响，演示照常。

令牌只在开发机的脚本里用，**不下发浏览器** —— 前端拿得到的令牌等于没有令牌。
所以界面上唯一的写动作（智能体回滚）走的是控制台既有的
`/api/admin/agents/{key}/rollback/{id}`，不在交付平台另开一条。
**两条路径改同一张表，迟早有一条忘了改。**

## 7. 智能体线为什么不走上报接口

控制台跑完回归后，在**同一个进程里**直接写 `delivery_runs`
（`app/delivery_lane.py`），不发 HTTP 给自己。上报接口要令牌是因为它从公网进来；
同进程再绕一圈 HTTP、再配一次令牌，只会多一个能配错的地方。

三条落在代码上的约束：

1. **写失败不影响回归结果。** 人是来看通过率的，不是来看看板的 ——
   写入包在 try 里，失败只发一条 `delivery_lane_write_failed` 事件。
   > 这条兜底第一次就派上了用场：`agent.name` 根本不存在（名字只在
   > `AGENT_REGISTRY` 里），异常被吞掉，是那行日志指出了 `AttributeError`。
2. **同岗位同档配置重复跑是更新。** 每跑一次多一条，看板上永远只看得见最后一次。
3. **没跑过的阶段报 idle，不替它填「通过」。** 「并排对比」是控制台里另一个动作，
   这次回归不知道它跑没跑 —— 不知道就说不知道。

## 8. 契约

| 方法 | 路径 | 令牌 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/delivery/pipelines` | — | 两条线各自最新一次运行 |
| GET | `/api/delivery/runs?lane=` | — | 运行列表 |
| GET | `/api/delivery/runs/{run_key}` | — | 单次运行 |
| GET | `/api/delivery/releases` | — | 合并时间线 + 回滚语义 |
| GET | `/api/delivery/production` | — | 生产指纹（两栏） |
| POST | `/api/delivery/runs` | ✔ | 上报运行，**同 key 为更新** |
| POST | `/api/delivery/releases` | ✔ | 记录功能发布，上一版转 superseded |
| POST | `/api/delivery/releases/feature/{commit}/rollback` | ✔ | 改状态并返回要跑的命令，`executed: false` |

两处刻意的返回值：

- **`stages` 会按模板补齐未开始的阶段。** 否则一条刚开始的运行看起来
  「只有一个阶段且已通过」，像是已经做完了。
- **功能回滚返回 `executed: false` + 命令原文。** 平台不持有生产凭据，
  不写清楚，「点了回滚」会被当成「回滚了」。

## 9. 脚本

```bash
# 门禁。行为与原来那串 && 完全一致，包括 fail-fast；多的只是结构化结果。
DELIVERY_API=https://da.aaronhealth.cn DELIVERY_INGEST_TOKEN=... npm run verify

# 部署。跑在开发机上 —— 生产凭据在这里，平台没有也不该有。
DELIVERY_API=https://da.aaronhealth.cn DELIVERY_INGEST_TOKEN=... npm run deploy
```

两个脚本的上报都是**尽力而为**：环境变量没配就不报，报失败只打一行警告。
门禁与部署是目的，遥测不是。部署期间容器会重启，那几秒的上报失败是常态不是故障。

`npm run verify:legacy` 保留了原来那串 `&&`，用于对照 —— 怀疑是新 runner
自己出问题时，跑一次它就能分清。

## 10. 还没做的

- **部署阶段的实时进度**：现在是分段上报（rsync 完一次、构建完一次），
  `docker build` 那六分钟里看板上只有「进行中」，没有逐层进度。
- **构建日志全文**：只留尾部 40 行。全文要落对象存储，一期不值当。
- **多环境**：见 §5。

## 11. 建这个平台第一天就抓到的两件事

平台本身没做什么聪明的判断，它只是**按退出码当真**。就这一条，抓出两个问题。

### ① 还原度门禁一直没在门禁

`compare-v43-fidelity.mjs` 从头到尾**只打印，从不设退出码**，永远 exit 0。
在原来那串 `npm run a && npm run b && ...` 里，它无论比出什么都放行 ——
所谓「146 元素零差异」是靠人盯着最后一行数字。

`verify.mjs` 按退出码判定，于是第一次跑就出现了荒唐的一行：

```
▸ 界面还原度 … ✓ 132 元素 · 一致 132 · 差异 0 · 缺失 14   ← 记成了通过
```

已补 `process.exit(diffs || missing ? 1 : 0)`。**缺失比差异更该拦** ——
差异是「长得不一样」，缺失是「这个元素根本没渲染出来」，
后者往往意味着整块功能没上。

> 顺带一提：`check-v43-coverage.mjs` 一直是有退出码的。两个脚本长得很像，
> 少的那一行谁也没注意到 —— 人读输出时，会不自觉地把「打印了失败」当成「失败了」。

### ② 那 14 个缺失是抖出来的，不是真缺

单独重跑是「缺失 0」。原因是取样的判据错了：`collect()` 在按下快门那一瞬间
`querySelector`，而那一瞬间取决于模型多快返回 —— 换到 Sonnet 5 之后，
`report-summary` 从 20 秒变成 60 秒，这个race 就开始输。

改成**取样前先并行等这些选择器 attached（20s）**。等过之后，
「缺失」才恢复它本来的含义：给了时间也没出现。

这是同一个教训第三次出现，前两次是 `networkidle` 和 Nginx 的 60s：
**等待的判据要是那个条件本身，不是一段时长。**

### 由此加的一条：通过的门禁也要留全量输出

发现「缺失 14」时，那 14 个是谁已经没了 —— runner 当时只在失败时打印尾部。
现在每一关的完整输出都写到 `build/gates/<key>.log`，**通过的也写**。

通过与否是结论，输出是证据。证据不该因为结论是「过」就扔掉。

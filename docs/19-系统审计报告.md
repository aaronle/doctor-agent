# 系统审计报告

日期：`2026-09-06`
范围：全仓 —— 测试体系、已知缺口、安全与数据边界、可靠性与可运维性
基线：`feat/delivery-platform`，线上 `0.3.0-mvp`（<https://da.aaronhealth.cn>）
目的：回答「离一个**真实可用**的系统还差什么」

一句话结论：**做出来的东西质量不低，但守护它的东西有几个洞是空的。** 临床红线的代码实现相当扎实（唯一事实源、硬规则独立于模型、五类降级兜底），问题集中在三处：谁都能改岗位配置、门禁有一条能被 curl 绕过、岗位调用其实没有超时。

## 一、P0：上真实数据前必须修

### P0-1　`/api/admin/*` 在公网上零鉴权

`apps/api/app/routers/admin.py` 全部端点的签名里只有 `Depends(get_session)`，**没有任何令牌或角色依赖**。已核实包括：

| 行 | 端点 | 后果 |
| --- | --- | --- |
| 247 | `save_draft` | 匿名改六个临床岗位的提示词、模型档位、`max_tokens` |
| 277 | `publish` | 发布即生效，不重启（`agents/base.py:217` 运行时读已发布配置） |
| 316 | `rollback` | 匿名回滚到任意历史版本 |
| 469 | `dry_run` | 匿名消耗模型额度 |
| 592 | `run_eval` | 匿名跑整个回归集 |

同时 `GET /api/admin/agents/{key}` 把 `running.role_prompt`、`code_default_prompt`、`safety_layer` 全文公开 —— 临床提示词资产等于公开。审计表里 `actor` 恒为 `DEMO_ACTOR`（`audit.py:14`），发生篡改**无法归因到人**。

对照组说明这不是能力问题而是遗漏：`routers/delivery.py:58` 的 `require_ingest_token` 已经做对了，且未配置令牌时 fail-closed 返回 503 而不是放行。`routers/config.py:44` 的 `PUT /api/config` 也已收敛为只读回显。

**修法**：`admin` 全部写端点套用 delivery 同款令牌依赖；反向代理层再加一道 Basic Auth + IP 白名单挡住 `/admin`、`/delivery`、`/api/data`、`/api/orchestration`。医生端接 SSO 后把 `actor` 落成真实工号。

### P0-2　写回门禁可被一条 curl 绕过

`routers/emr.py:980` 的 `_assert_red_alerts_closed` 判据是：

```python
open_red = sorted(all_red - set(handled or []))
```

`handled` 来自**请求体**（`DiagnosisWriteBackIn.handled_alerts`），服务端从不与库里的 `patient.payload["handled_alerts"]` 比对。而 `GET /api/emr/red-alerts/{pid}` 匿名就能读到全部 alert id，回填进请求体即通过。

函数注释写着「不信任前端的按钮禁用状态」—— 它确实不信任按钮，却完全信任请求体里这个数组，等于没拦。

第二处：模型侧红色风险取自**进程内缓存**（`cache.py`，30 分钟 TTL，重启即空，`emr.py:1003`）。缓存不命中时 `model_alerts` 为空，门禁分母只剩硬规则 —— 和上面是同一个洞的另一种触发方式。

**修法**：`handled` 只从库里读，请求体那个字段直接删掉；模型红线落库，不用进程缓存。**并补一条能失败的测试** —— 现有的 `test_server_side_gate_blocks_write_back_even_if_frontend_bypassed` 测的是「前端被绕过」，没测「请求体被伪造」。

### P0-3　六个岗位的模型调用根本没有超时

这条最隐蔽，且**文档与 env 注释都写反了**。

`config.py:57` 的 `timeout_seconds` 唯一消费者是 `llm.py:151` 的 `httpx.AsyncClient(timeout=...)`，而 `llm.py` 现在**只剩流式路径**（Copilot 对话、病历流式）。六个岗位走 `agents/runtime.py` → `model_gateway.build_chat_model()`，其 `client_kwargs` 里只有 `base_url` 和 `max_retries: 4`，**没有 `timeout`** —— openai SDK 默认 600s。

后果链条：

- 网关不返回时，单岗位可挂 600s × 5 次尝试。
- `agents/base.py` 只在**异常**时降级，**永远不会因超时降级** —— `degraded_agents` 这套设计在最需要它的场景里失效。
- 真正切断的是 Nginx（`report-summary` 180s），医生看到的是空白 504，而不是「已降级 + 本地规则」。
- 叠加放大：`SCHEMA_RETRIES = 2` × SDK `max_retries: 4` × 无超时。risk 岗位单次 52.2s，schema 重两次就是约 156s，已经贴住 Nginx 的 180s。

**修法**：

1. `build_chat_model` 的 `client_kwargs` 加 `timeout`（建议 `httpx.Timeout(connect=5, read=90)`）。
2. `_run_isolated` 外包一层 `asyncio.wait_for`，给每个岗位一个**墙钟预算**（建议 75s，含 schema 重试），超时走 `fallback()` 并计入 `degraded_agents`。这是唯一能保证 `report-summary` 一定在 Nginx 之前返回的办法。
3. **加一条测试钉住 `build_chat_model` 必须带 timeout。** 这个项目已经因为「env 盖住代码缺省、没人看 health」栽过两次（HANDOVER §8 的 09-02 两条），同类问题要用测试守，不能靠纪律。

### P0-4　零限流，成本敞口敞开

全仓唯一的并发控制是 `admin.py:613` 回归集的 `Semaphore(3)`。没有任何按 IP 或会话的限流。可被循环打的端点：

| 端点 | 单次成本 |
| --- | --- |
| `GET /api/emr/report-summary/{pid}?refresh=true` | 4 个 Sonnet 并发，绕过缓存，18–60s |
| `POST /api/orchestration/ask` | Master 串 6 worker，ReAct 最多 12 轮，实测 100–200s |
| `POST /api/admin/agents/{key}/eval` | 整个回归集 |

放大器：`schemas.StrictIn` **没有任何 `max_length`**，Nginx `client_max_body_size 1m` 是唯一上限 —— 单个 `question` 可塞约 25 万 token，再乘 ReAct 轮次重放。且 `AI_API_KEY` 与 `ts-it-service` **共用同一把**，刷穿会连累工单系统。

**修法**：Nginx `limit_req` + 入参 `max_length` + 网关侧月度预算告警。这条建议一期就修，与是否上真实数据无关。

## 二、P1：影响可靠性，建议尽快

### P1-1　SQLite 无备份、无迁移、无 WAL

- **无备份。** 全仓唯一的 `.bak` 出现在 `demo-reset.mjs:61`，那是重置演示态时顺手拷的一份，不是备份机制。`agent_runs`（275 条）与 `audit_logs` 文档标着「永久保留」「合规追溯」，实际存在一个 3.4MB 单文件里，**没有任何副本**。轻量云盘故障 = 全部审计证据消失。
- **无迁移。** `find -iname "*alembic*"` 零结果，而 `database.py:20` 的 docstring 白纸黑字写着「正式环境的可追溯迁移仍由 Alembic 负责」。实际只有 `create_all` + `PRAGMA table_info` 差集补 `ALTER ADD COLUMN` —— 只能加列，改类型、加约束、改列名、数据回填一律做不了。`voice_sessions` 表名与 `InterviewSession` 类名长期不一致就是它的第一笔利息。
- **无 WAL。** 四岗位并发写 `agent_runs`（`base.py:_record` 每次 `session.commit()`），默认 rollback journal 下写锁争用会抛 `database is locked`，而 `_record` 在 try 之外，会**直接 500**。

**修法**（半天）：宿主机 cron `sqlite3 db ".backup /opt/doctor-agent/backup/da-$(date +%F).db"`（**用 `.backup` 不用 `cp`**，前者对在线库是一致性快照）+ 保留 14 天 + 每周一份传对象存储；开 `PRAGMA journal_mode=WAL`；要么真引入 Alembic，要么把那句 docstring 改成实情。

### P1-2　63 秒等待，且四个岗位原子返回

`emr.py:326` 的 `asyncio.gather` 四岗位并发，总耗时 = 最慢的 risk（52.2s）。`15-…md §15` 已用数据否掉「换 Haiku 提速」这条路。

项目已经做了正确的缓解 —— `red-alerts` 毫秒级返回硬规则危急值、首屏不等分析、63 秒藏在问诊说话的时间里。**设计是对的，不必推翻**。但仍有两处硬伤：

- 前端只有一个 `loadingSummary` 布尔量（`stores/workstation.ts:33`），63 秒里没有任何进度信息，医生无从判断是不是卡死。
- summary 25.5s 就好了，却要陪 risk 等到 52.2s。

**修法**：`/report-summary` 改 SSE 增量返回。基础设施全现成（`SSE_HEADERS`、`_stream_chat`、Nginx `proxy_buffering off` 都在跑）。`asyncio.as_completed` 替代 `gather`，每个岗位完成推一个事件，前端分块渲染 —— **感知等待从 63s 降到 25s，且每块到达都是可见进度**。缓存逻辑不受影响（全到齐后再 `cache.put`）。

### P1-3　静默降级无人察觉

好的一面：八个岗位**全部实现了 `fallback()`**，基类声明为 `NotImplementedError`，漏写会运行时炸而不是静默；降级结果不入缓存，避免一次抖动锁死半小时。

问题在标注与发现：

- 桌面端 `WorkstationView.vue:278` 只显示「N 个智能体已降级」的**计数，不说是哪一个**；移动端反而显示了名字。而降级的是 risk（漏一条风险）还是 comorbidity（少一段共病），临床含义天差地别。
- `useInterview.ts:228` / `useFollowUp.ts:73` 在 degraded 时**直接把结果丢成空数组**，界面上「没有待补问」和「问诊很完整」长得一模一样。
- **§18 那个教训还没有守护**：`interview_agent` 从上线起 100% 降级，没有告警、没有测试失败、界面看不出来，是做别的功能时顺手量出来的。提示词已修好，但下一次同类静默降级仍然靠运气发现。

**修法**：桌面端展示降级岗位的中文名并就地标注；降级时不要清空成空数组，改为显式「本项未能评估」；加每日巡检 —— `agent_runs` 按 `agent_key` 聚合近 24h 的 `status='degraded'` 占比，任一岗位 >20% 就报。数据已在库里，写个查询就行。

### P1-4　可观测性只有日志，没有监控

四层日志的划分是清晰的，`obs.py` 的三条约定都有测试守着。但：

- `llm_call` **只在 `llm.py` 里发**，即只覆盖流式路径。六个岗位**没有通道层事件**，SDK 那 4 次重试完全不可见 —— 而 `13-…md` 的埋点表声称 `llm_call` 能看出重试了几次，对岗位调用不成立。
- **没有 trace/request id。** 四岗位并发时日志里四条 `agent_run` 靠 `patient` 关联，同一患者两次刷新就分不清。
- 日志轮转 `max-size 10m × 3`，**结构化事件保留期只有几天**，而它是唯一记录「为什么降级」的地方。
- **告警完全没有。** 没有 Prometheus、没有 Sentry、没有 cron 巡检，全靠人 ssh 上去 `docker logs | jq`。

### P1-5　`obs._REDACTED` 不够全，正文可能进日志

缺 `note_text`、`question`、`task`、`answer`、`messages`、`summary`、`detail`、`raw_excerpt`、`chief_complaint`、`user`、`system`。而 `agents/base.py:252` 确实在记 `detail=str(exc)[:160]` —— `GenerationError` 的消息可能携带模型原文片段，也就是病历文本。另外 `_clean` 对非标量做 `str(value)[:120]` 落盘，任何 dict 都会漏 120 字。

一期是虚构数据所以无害，**真实数据下这就是病历碎片进 `docker logs`**。修法：改成白名单，只允许显式声明的标识与度量键。

### P1-6　`copilot/chat` 是安全层的唯一缺口

`agents/safety.py` 的 `SAFETY_LAYER` 是全仓唯一一份红线，产品路径与编排路径都共用且都排第一 —— 这个结构是对的。但 `POST /api/emr/copilot/chat`（`emr.py:633`）用的是**另一段硬编码的三行 system**，不含 `SAFETY_LAYER`，且 `messages` 原样透传。

另外「顺序即优先级」只是约定：`/admin` 里写的 `role_prompt` 拼在安全层之后，没有任何机制阻止它写「忽略上述红线」—— 而那个接口无鉴权（P0-1）。

## 四、功能缺口

按「医生一眼能看出破绽」排序：

1. **33 项专项评估里 31 项 `desc` 为空字符串**，医生点开条目得到一个空白框（`AiEmrFloat.vue:1845` 无空值兜底）。这条没被任何文档记为缺口。
2. **转诊、住院两条后端路径界面上完全不可达**。`api.ts:683-685` 定义的 `createReferral` / `createAdmission` 全仓找不到调用方，而 `his.py:315,338` 已实现。
3. **九个处置类对话框缺八个**。只有「开立医嘱」「开立检查/检验」落地。「发起共病会诊」有按钮无确认弹层，一点即提交 —— 与「每个有后果的动作都要医生确认」相悖。
4. **推荐医嘱是种子不是模型输出**（`emr.py:360`），界面上无任何标识区分 —— 而降级路径都有显式标注，这块反而没有。
5. **F07 `control_status` 未实现**（`18-规格符合性走查.md` §三B 已定性）。
6. **33 项专项评估零执行**：纯展示，无 `@click`、无任务状态机、无 `risk_id` 回指 F06。`07-…md` 的 `AC-SA-004/005/006/009/010` 全部未满足。
7. **AI 处置单整块下线但后端留活**：`TODO_CATEGORY` 与 `_build_todos` 仍在跑、仍有 5 条契约测试，前端零消费。10 号文 §10.2.1 声明是有意保留 —— 记账清楚，但它是当前唯一的成建制死代码。
